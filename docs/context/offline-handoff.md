# 사내망 격리 이전 핸드오프 — 외부 협업 맥락과 Phase 0 실측 상태

> **목적:** 외부 GitHub·외부 LLM·기존 대화 기록에 접근할 수 없게 되어도, 사내의 승인된 개발 환경에서 프로젝트를 이어갈 수 있도록 맥락과 검증 경계를 남긴다. **데이터 반출 또는 사내 보안 정책 우회 방법을 안내하지 않는다.** 이 문서는 이전 전에 만든 공개/외부 작업 산출물만 대상으로 한다.
>
> **상태 기준:** 2026-11-16, 사내망 이전 전 외부 저장소의 Phase 0 개발 결과. 이후 변경은 **사내 Git/사내 문서**가 유일한 최신 기준이 될 수 있다. 아래 테스트는 당시 개발 호스트/합성 데이터의 결과이며 새 사내 호스트에서의 시험을 대신하지 않는다.

## 2. 외부에서 마지막으로 확인한 코드 기준

- Phase 0 작업 브랜치: **feat/p0-5-mcp-operations**, 통합 구현의 마지막 기존 커밋은 **f4bbfe8** (이전 P0-1, P0-2~P0-4 이력 포함).
- 이 브랜치에는 Experience·Receipt·Job, Worker/Reference Engine/검색, 삭제·권한·수동 정정, Generation/Rebuild, MCP/REST, Compose/TLS, 백업·복구 정책 ledger, 관련 자동 시험이 포함된다.
- **합성 데이터 기준 개발 기록:** Ubuntu 24.04 / Python 3.12 / PostgreSQL 16에서 187 passed, 8 skipped(Compose E2E opt-in); 별도 Compose E2E 8 passed. 레거시 Ubuntu 20.04 컨테이너 / Python 3.8 / PostgreSQL 12에서 166 passed, 4 skipped. **독립적인 사내 호스트 실측은 아니다.**
- P0-5는 **부분 완료**: 실제 VS Code Copilot에서의 C1~C8 에이전트 동작, 실제 외부/사내 배포 호스트와 조직 CA/TLS, 실제 Ubuntu 20.04 호스트를 검증하지 않았다.
- **개인·업무 실데이터 운영 승인으로 해석하지 않는다.** 개발용 CA·localhost·합성 데이터 통합 시험의 성공과 사내 보안 운영 승인은 다른 단계다.

Git의 병합 방식이나 날짜보다 중요한 것은 **실제로 이전하는 commit SHA와 모든 파일/의존성의 무결성**이다. 내부 저장소가 이 외부 브랜치와 달라진 순간, 이 문서의 테스트 수치는 참고 기록일 뿐이다.

## 3. 격리 이전에 보존할 대상과 경계

조직의 정식 반입 절차에 따라 확인할 수 있는 자산:

| 자산 | 왜 필요한가 | 주의 |
| --- | --- | --- |
| Git 이력/브랜치/커밋 | 구현 의도, 회귀와 변경 이력, 원본 추적 | 파일만 압축하면 Git 이력이 사라짐. 외부 remote를 내부 origin으로 오인하지 말 것 |
| 설계·연구·운영 문서 | 외부 대화가 없어도 방향성을 복원 | URL은 내부에서 열리지 않을 수 있음. 핵심 해설은 이 문서에 있음 |
| 의존성 버전/라이선스/패키지 아티팩트 | 폐쇄망에서 재현 가능한 빌드 | 패키지·컨테이너 이미지 반입 및 사용 라이선스는 조직 승인이 필요 |
| Docker/Compose 및 PostgreSQL 환경 | API/Worker/DB/프록시 통합 시험 | 내부 DNS/IPAM/CA/포트/커널 제약은 외부 개발 호스트와 다름 |
| 테스트와 합성 fixtures | 사용자가 없는 환경에서도 기능 검증 | 합성 데이터에 실제 회사 코드/이름/비밀을 섞지 말 것 |
| 마이그레이션과 운영 도구 | 빈 환경에서 DB 생성, 삭제/복구 검증 | 테스트용 SUPERUSER 설정을 실제 서비스에 적용하지 말 것 |
| 증거 파일·검증 로그 | 당시 한계/성공 조건을 이해 | 접근 토큰·DB URL·사내 정보가 들어간 로그를 외부에 올리지 말 것 |

가능하다면 **조직이 허용하는 절차로 Git 저장소 전체 및 필요한 의존성 아티팩트를 내부로 반입**하고, 반입 직후의 commit SHA·파일 체크섬·이미지 digest·선택 버전을 기록한다. 내부 DNS/registry/package mirror 접근 여부는 실제 환경에서 확인한다. 인터넷이 없다는 이유로 출처 불명의 패키지를 조용히 대체하거나 보안 검증을 끄지 않는다.

**주의:** 사내 반입 후 생기는 코드는 외부 GitHub, 공개 원격 Git 서버, 일반 채팅/LLM, 원격 CI, 외부 오류 분석/telemetry, 개인 메일·클라우드 파일 공간으로 **반출하지 않는다.** 개발·디버깅·외부 리뷰도 조직이 승인한 데이터 경계 안에서 수행한다. 외부에 질문할 필요가 있다면 회사 규정이 허용하는 추상적인 설계 질문만 사용하고 내부 코드는 첨부하지 않는다.

## 4. Copilot/Agent를 사용하는 경우의 특별한 주의

이 프로젝트의 초기 클라이언트 목표는 GitHub Copilot Agent였지만, **사내망에서 사용할 수 있는 Harness/모델과 그 네트워크 경로가 실제로 승인되어 있는지는 별개의 문제**다. 외부 서비스에 코드나 문맥이 전송되는 사용 방식은 사내 반출 금지 규정과 충돌할 수 있다. 조직이 승인한 Copilot 구성/내부 제공 모델/에이전트만 사용한다. 사용 가능 여부를 가정하지 않는다.

Copilot 자체 클라우드 메모리는 사용자 설명상 조직 정책으로 막혀 있고 로컬 메모리 옵션은 사용하지 않았다. 이 조건은 **당시 사용자 진술이지 사내 모든 PC/버전의 검증 결과가 아니다.** Memory Server와의 충돌보다 Agent가 실제로 MCP 도구를 발견·호출·활용하는지가 주된 검증 질문이었다.

클라이언트 설정은 Harness/버전에 따라 **MCP 설정 파일 경로·최상위 키·변수 보간·정적 Authorization 헤더 지원이 달라질 수 있다.** 저장소의 VS Code 예시는 당시 검토 대상이며, 사내 PC의 실제 Copilot/VS Code 버전과 조직 정책에서 재검증해야 한다. 외부에서 "될 것"이라고 추측한 설정을 검증 완료로 표시하지 않는다.

클라이언트 검증에서 구분할 결과:
- MCP 도구 연결/초기화가 실패함.
- 연결은 됐지만 적절한 상황에서 memory_search를 호출하지 않음.
- 호출했으나 검색 결과가 비어 있음(키워드·언어·엔진 문제).
- 결과를 반환했지만 답변에 활용하지 않음.
- 오래된 기억/신뢰할 수 없는 내용을 최신의 검증된 사실로 취급함.

## 5. 실제 데이터 도입 전에 사내에서 별도로 판단할 것

Phase 0가 외부 개발 호스트에서 동작했다는 것만으로 사내의 정식 데이터 취급·보안 승인을 뜻하지 않는다.

- 인증/토큰 발급·철회/기기별 권한, 사내 Host·Origin·방화벽·TLS/조직 CA 정책.
- DB와 백업의 암호화, 별도 위치의 암호화 백업, **삭제/철회 후에도 최신이어야 하는 정책 ledger의 독립 보존**.
- 컨테이너·패키지의 지원 버전/취약점/라이선스 및 오프라인 패치 경로.
- 서버 재시작/정전/디스크 부족/DB 장애·복구, 실제 커널/네트워크 성질.
- 로그에 원본·검색어·인증 비밀·조직 정보가 남는지, 접근·보관 정책.
- 외부 LLM/모델로 경험 원문이 전송되지 않도록 구성된 실제 승인 경로.
- 데이터 보존·삭제의 법적/조직적 의미. **DB 검색 비노출, 운영 저장소 삭제, 이미 만든 백업의 물리적 삭제는 서로 다르다.**

현재 코드의 정책 ledger는 삭제·철회·권한 축소 기록을 DB 외부에 해시 체인으로 남기고 격리 복구 중 재적용하도록 했다. 하지만 ledger가 항상 최신이라는 것을 자동으로 증명하지 못하며, 외부 재해에 안전한 복제도 자동으로 구현된 것은 아니다. **최신 정책 이력이 없으면 오래된 백업을 공개하지 않는 fail-closed 기본값**이 중요하다.

## 6. Phase 0의 가치와 아직 남은 검증

**이미 얻은 기반:** 원본/파생 구분, 비동기 처리를 포함한 작은 수직 경로, 기본 검색, 접근 권한, 삭제/철회, Reference Engine 두 버전, Generation 비교·전환, 복원 중 격리. 이들은 장기 엔진 연구의 출발점이다.

**그렇다고 증명하지 않은 것:** 자동 기억 수집과 자발적 검색, Copilot의 실제 활용, 자연어 표현이 바뀐 질문의 좋은 recall, MemoryLACE/Hindsight 수준의 기억 통합, 실제 사내 네트워크/운영 복구.

사내에서 최초의 합성 데이터 사용 경험을 만들면 [연구 평가 지도](../research/future-experiments-and-questions.md)에 있는 **수집/가공/검색/전달/사용/정책**의 실패 구분을 적용할 수 있다. 사용자·조직의 데이터가 들어가기 전에 충분히 격리된 시험 환경에서 검증할 것을 권한다.

## 7. 외부와의 단절이 연구를 멈추게 하지는 않는다

논문 소스 코드와 GitHub URL은 참고용이지, 이후 개발을 계속하기 위한 실시간 의존성이 아니어야 한다. Hindsight/MemoryLACE에서 얻은 **증거와 추론 분리, 시간·상충/대체 상태, 국소 관계, 다중 검색 전략과 비용**에 대한 문제의식을 이 저장소에 요약했다.

이후 내부에서 수행할 연구는 이 문서의 특정 방법을 복제할 의무가 없다. 실제 사용 중 발견되는 새로운 실패와 제약을 우선한다. 원본/권한/삭제를 지키면서 더 나은 기억을 만드는 방법을 검증하되 **기존 데이터에 대한 접근과 복구를 잃지 않도록** 한다.

## 8. 문서와 저장소 관리

- 내부 저장소의 **main 또는 사내에서 합의한 기준 브랜치**가 이후 최신 source of truth다. 외부의 원래 main이 계속 갱신된다고 가정하지 않는다.
- 실험 결과가 초기 설계를 뒤집는 경우 그 이유와 관측을 내부에서 기록하고 적절한 설계 버전을 남긴다. **확정된 합의와 가설/보류/실패한 실험을 구분**한다.
- 연구 메모에는 실제 내부 코드/데이터를 외부로 복사하지 않는다.
- 비밀 파일, 인증 토큰, DB 덤프, 운영 정책 ledger, 사내 디렉터리/고객 자료는 Git에 넣지 않는다.
- 본 문서와 다른 문서가 충돌하면 **실제 내부 구현·테스트 결과를 확인**하고 수정한다. 오래된 설명을 사실처럼 밀어붙이지 않는다.

**마지막 메시지:** 이 프로젝트는 "어느 메모리 논문의 구조가 맞는가"를 미리 결정한 프로젝트가 아니다. **장기 경험의 소유권·출처·재처리를 지키면서, 여러 Agent가 실제로 쓸 수 있는 더 좋은 기억을 점진적으로 찾아가는 프로젝트**다.
