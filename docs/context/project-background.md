# 프로젝트 배경과 설계 방향 — 대화 맥락 보존 기록

> **성격:** Phase 0 이후의 개발자·에이전트에게 전달하는 배경 설명. 2026-11-16까지의 프로젝트 논의와 저장소의 Architecture/MVP/Phase 0 설계·리뷰 이슈를 바탕으로 정리했다. **새로운 구현 명령, 확정된 알고리즘, 변경 불가능한 ADR이 아니다.** 사실·합의·가설·미결정을 구분해서 읽는다.
>
> **중요:** 사내망으로 이전한 뒤의 코드·데이터·진행상황은 외부 GitHub/공개 LLM으로 반출할 수 없다는 전제를 따른다. 이 문서는 **이전 이전**에 외부에서 논의하고 구현한 배경만 담고 있으며 사내 자료를 포함하지 않는다.

## 1. 왜 시작했는가

사용자는 VS Code의 GitHub Copilot Agent로 개발하지만, 장기 기억을 특정 LLM, 공급자 또는 Agent Harness 내부에만 맡기는 방식의 한계를 고민했다. PC가 바뀌고, 세션이 끝나고, 에이전트를 Claude Code나 다른 도구로 바꿔도 프로젝트의 누적 경험과 중요한 결정이 이어져야 한다. 서로 다른 클라이언트가 **같은 원격 메모리 자산**을 이용할 수 있도록 개인 소유의 서비스를 만들고자 했다.

그렇다고 "대화 기록을 DB에 저장하고 검색"하는 것만 최종 목표로 생각하지 않는다. 장기적으로는 어떤 경험이 기억으로 굳어지는지, 이미 알고 있던 내용과 어떻게 합쳐지는지, 어떤 기억이 쉽게 떠오르고 어떤 기억은 깊이 검색해야 나오는지, 변경·모순·망각을 어떻게 다룰지를 연구하고 싶었다. **처음부터 인간의 기억을 정확하게 모사하겠다는 약속은 아니다.**

상용·오픈소스 엔진 하나를 사용해도 처음에는 편할 수 있다. 그러나 엔진의 표현이나 통합 규칙을 바꾸고 싶어지는 순간 원본·출처·권한·수명주기가 엔진 내부에 얽혀 있다면 전체 시스템을 다시 만들어야 한다는 우려가 출발점이었다.

따라서 **엔진을 나중에 교체하기 위한 플랫폼을 크게 만들자**가 아니라, **엔진이 변하더라도 기존 경험과 권한 정책을 보존하고 비교·재처리할 수 있는 작은 시스템부터 만들자**라는 방향을 택했다.

## 2. 지향점과 성공의 의미

- **Harness/모델 독립성:** Copilot을 첫 실제 클라이언트로 사용하더라도 MCP는 여러 접근 방식 중 하나다. Claude Code·Codex·향후 클라이언트까지 염두에 둔다.
- **여러 PC와 세션의 연속성:** 한 클라이언트가 제출한 경험/기억을 적법한 다른 클라이언트가 다시 활용한다. 자동 수집·자동 호출은 MCP 연결만으로 보장되지 않는다.
- **Experience와 Memory의 분리:** 원본 경험과 엔진이 생성한 파생 기억을 논리적으로 다르게 취급한다. 원본이 유효하고 허용된 범위에서 재처리할 수 있어야 한다.
- **Provenance와 시간:** "무슨 내용인가"뿐 아니라 누가, 언제, 무엇을 제출했고 어떤 엔진/설정이 어떤 결과를 만들었는지 중요하다. 제출된 주장과 서버가 검증한 사실을 구별한다.
- **소유권과 거버넌스:** 원본·파생 결과·검색/관계·이전 세대에 걸쳐 접근 권한과 삭제 정책이 적용돼야 한다.
- **검증 가능한 성장:** 알고리즘을 도입했다는 사실보다 이전 기준선보다 더 잘 회상하고, 더 적게 잘못 회상하고, 그 비용과 부작용을 설명할 수 있는지가 중요하다.
- **단순한 시작:** 서버/Worker/DB의 모듈형 모놀리스, REST·MCP 얇은 어댑터, 작은 Reference Engine. 실제 필요성을 확인하기 전에 Graph DB, 범용 플러그인 프레임워크 또는 무중단 이중 쓰기를 도입하지 않는다.

**성공은 단일 점수가 아니다.** 시스템이 원본을 안전하게 저장하는 능력, 엔진이 유용한 기억을 형성하는 능력, 서버가 관련 기억을 반환하는 능력, 실제 에이전트가 이를 호출하고 사용하는 능력은 각각 측정되어야 한다.

## 3. 이 프로젝트에서 특히 중요하게 구별한 것

### Experience, 명시적 기억, 파생 기억

- **Experience:** 대화·문서·개발 과정 또는 명시적 메모로 제출된 원천 기록과 그 수집 정보. 원본 자체가 검증된 진실이라는 뜻은 아니다.
- **Explicit Memory:** 사용자/에이전트가 "기억하라"는 의도로 제출한 텍스트. Phase 0에서는 원문을 고치지 않고 보존한다. 에이전트가 제출했다고 실제 사용자가 승인한 사실은 아니다.
- **Derived Memory / Artifact:** 특정 엔진 버전이 경험을 바탕으로 생성한 검색·추론용 결과. 엔진의 내부 표현은 미리 Narrative/Atomic/Opinion 중 하나로 강제하지 않는다.
- **Generation/Index:** 어떤 파생 결과 집합이 어떤 처리 버전으로 만들어졌고 현재 검색에 사용되는지 나타내는 구분. 단순 백업 버전과는 다르다.

Hindsight의 **world/experience/observation/opinion**은 연구 논문의 기억 분류이며, 이 저장소의 **Experience 원본/Memory Artifact** 구분과 일대일로 대응시키지 않는다. 미래의 엔진이 그 개념을 선택하면 그때 연결을 설계한다.

### 사실, 주장, 해석, 의견, 결정

지난 대화에 "이런 기술을 쓰자"는 문장이 있어도 그것이 현재 코드에 구현되어 있다는 뜻은 아니다. 사용자 결정인지 Agent의 재구성인지, 확정 결정인지 잠정 검토인지, 지금도 유효한지 나눠야 한다. 의견이나 추정은 근거 있는 사실과 구분돼야 하며, 오래된 결정은 시간/상태를 함께 취급해야 한다.

### 데이터 삭제, 접근 철회, 알고리즘적 망각

- **삭제:** 정책상 더 이상 보존하거나 노출하면 안 되는 원본/파생 데이터를 다룬다. 이전 세대와 복구 경로에도 재노출 방지가 적용돼야 한다. 운영 DB 비노출과 백업 포함 물리 소거는 다른 보장이다.
- **기기/주체 철회:** 그 주체가 더 이상 접근하지 못하게 하는 것이다. 다른 적법한 클라이언트의 공유 기억을 일괄 삭제하는 일이 아니다.
- **알고리즘적 망각:** 기억을 얼마나 쉽게 찾거나 우선 회상할지, 압축할지, 보존 강도를 어떻게 바꿀지의 문제. 데이터 삭제 정책과 같은 연산으로 보지 않는다.
- **기억 정정/대체:** 어떤 주장이 바뀌었다고 항상 과거 증거를 지워야 하는가? 과거 상태는 역사적 질문에 필요할 수 있다. 자동 정정/모순 해결의 구체 규칙은 아직 결정하지 않았다.

### 저장 지속성과 회상 접근성

**기억이 남아 있다는 것**과 **일상적인 질문에 쉽게 떠오른다는 것**은 같지 않다. 장기 연구 아이디어에는 기억의 지속·강도와 검색에서의 접근성을 서로 다른 차원으로 모델링할 수 있는지, 잊힌 듯한 기억을 깊은 검색이나 새로운 문맥으로 다시 활성화할 수 있는지가 포함됐다. **구체적인 감소 함수, 확률, 가중치, 시계 모델은 합의하지 않았다.**

### MCP 연결과 실제 에이전트 행동

도구가 등록됐다는 사실은 에이전트가 적절한 순간에 그 도구를 부른다는 증거가 아니다. 원격 MCP, REST, Hooks/Importer 등은 **수집·호출 방식을 달리하는 경로**이다. 서버가 검색 후보를 발견했는지(retrieved), 응답에 보냈는지(returned), 클라이언트가 사용했다고 보고했는지(client-reported-used)를 구분한다. 후자의 실제 사용은 보고나 별도 관측 없이는 단정할 수 없다.

## 4. 지금까지 정한 시스템 경계와 그 이유

| 주제 | 현재 방향 | 왜/언제 재검토할까 |
| --- | --- | --- |
| 서비스 구성 | 단일 개인 원격 서버에서 Modular Monolith + Worker + PostgreSQL | 작은 규모에선 운영·트랜잭션 경계가 단순함. 실제 부하·배포 요구 시 재검토 |
| 프로토콜 | MCP/REST는 하나의 Application Service 위 얇은 어댑터 | 특정 Harness와의 결합을 피함. 실제 클라이언트 인증/호출 차이는 검증 필요 |
| 원본/결과 | 원본 Experience와 Memory Artifact/Job/Generation의 상태·출처 분리 | 엔진 품질과 인프라 문제를 따로 발견하고 재구축하기 위해 |
| 엔진 인터페이스 | 처음에는 작고 구체적인 내부 경계만 구현 | 두 번째 *다른 구조의* 엔진에서 부족한 점이 드러나면 확장 |
| Phase 0 원본 | 작은 텍스트는 PostgreSQL 트랜잭션에 포함 | 파일+DB 장애 처리를 늦춤. 첨부/대용량엔 별도 정책 필요 |
| Rebuild | 격리 Generation, 기준 원본 집합 비교, 임시 입력 중단·수동 활성화 | 작은 구현을 검증하기 위한 단순화. 긴 처리/상시 사용이 늘면 재검토 |
| 인증/삭제 | 서버 중심 권한, 모든 세대/파생 결과에 정책 적용, 늦은 Worker 결과 차단 | 개인용이어도 사내·개인 범위 혼합이 민감할 수 있음 |
| Reference Engine | 명시적 문구 보존 + 일반 원본 투영 + 결정론적 키워드 검색 | **Phase 1의 비교 기준선.** 복잡한 기억 형성 능력을 증명하지 않음 |

Phase 0의 **실제 근거 관계(evidence_refs) 생성은 보류**했고, locator는 비검증 위치 주장으로만 보관한다. 잘못 저장한 명시적 기억은 관리자가 삭제하고 새 Experience로 제출하는 수동 정정으로 시작했다. 여기서 보류한 강한 근거 의존성/자동 정정은 영구 금지된 기능이 아니다.

## 5. 무엇을 확정하지 않았는가

아래는 지금 "정답"으로 만들지 않는다.

- Hindsight나 MemoryLACE, 기타 엔진의 채택/재구현 여부.
- 기억의 기본 단위를 Narrative, Atomic, 이벤트, entity profile 등 무엇으로 삼을지.
- 새 경험에서 무엇을 자동 추출할지, 무엇을 정리·통합할지, 사실/주장/의견의 검증 수준.
- 기억 관계를 그래프로 저장할지, sparse lifecycle 링크로 충분할지, 둘을 혼합할지.
- 중요도·최근성·반복도·상황 유사성·접근성·유지 강도 등의 점수와 업데이트 함수.
- bounded consolidation, 깊이 제한된 multi-hop 검색, 통합 전후 출처 유지, 망각/재활성화 방식.
- 임베딩·Reranker·LLM 종류, 로컬 모델과 외부 모델의 경계, 추론 비용/지연 예산.
- 로그·피드백의 민감성·보관 범위 및 개인/업무/프로젝트별 실제 분리 모델.
- 엔진의 완전한 상태 재생성이 원본만으로 충분한지. **사용·시간·통합 이벤트를 소비하는 엔진에는 추가 상태와 사건 기록이 필요할 수 있다.**
- 다중 사용자 OAuth, 대규모 저장소, 자동 무중단 Rebuild, 범용 엔진 플러그인 프레임워크.

미결정을 방치한다는 뜻은 아니다. **실사용 실패 사례와 엔진 비교 실험의 증거가 생겼을 때 결정하자**는 선택이다.

## 6. Phase 0과 이후의 관계

Phase 0는 기반 시스템의 진위를 확인하고 **처음부터 사용할 수 있는 Reference Memory Engine**을 제공한다. 즉 "버릴 Dummy"가 아니라 최초의 baseline이다. 실제 Copilot·다른 Harness에서 명시적 기억 저장→새 세션 검색→출처 확인을 하면서 검색 누락·사용 실패·동작 비용을 기록한다.

Phase 1은 특정 논문을 그대로 구현하는 단계로 예약해 두지 않았다. "이유를 설명하지 못함", "변경된 결정의 과거와 현재를 혼동함", "한국어 표현 차이로 못 찾음", "적은 증거로 과도한 요약을 함" 등 실제 관측에서 문제를 찾고 **왜 지금의 기준선보다 나은 처리가 필요한지**를 먼저 판단한다.

더 복잡한 엔진이 **품질 이득 없이** 비용·운영 위험만 키운다면 도입하지 않을 수도 있다. 기존 Reference Engine이 여전히 유용하다면 계속 운용하고, 새 엔진은 같은 경험/평가 질의의 비교 대상으로 취급한다.

## 7. 클라이언트 내장 메모리와의 관계

처음에는 Copilot 자체 메모리와의 충돌을 우려했다. 이후 사용자는 **클라우드 Copilot Memory는 조직 정책으로 차단**, **로컬 Copilot Memory 옵션은 미사용**이라고 설명했다. 이 조건이 해당 Copilot Harness에서 실제로 모두 적용된다면 **동시 활성된 두 장기 기억 저장소의 충돌은 주요 문제가 아닐 수 있다.** 다만 정책·클라이언트 버전은 환경별로 확인해야 한다.

여전히 코드는 현재 구현 사실을, Git으로 관리되는 설계 문서는 문서화한 결정을, 채팅 컨텍스트와 AGENTS.md 등은 작업 지침을, 외부 Memory Server는 이전 경험·명시 기억을 제공한다. **기억은 항상 가장 높은 권위의 사실이나 명령이 아니다.** 상충할 때 출처·시점·현재 코드/결정 문서를 확인해야 한다. 과거 기억을 시스템 프롬프트나 도구 권한으로 승격해서는 안 된다.

## 8. 사내망 격리 이후의 개발 원칙

외부 GitHub에 접근하지 못하고 외부로 코드·문서를 반출할 수 없다면, **이 문서와 저장소만으로 연구 이유·현재 구현·향후 질문을 복원할 수 있도록** 한다. 앞으로의 결정과 실험은 사내 승인된 저장소·문서·로그에서 이어간다. 외부 도움을 받는 경우 조직 정책상 승인된 **비식별·추상화된 질문**만 다루고, 코드·경로·구성·토큰·사용자 데이터·내부 결과를 임의로 반출하지 않는다.

이전 이후에는 사내 관측 결과가 외부 저장소의 이력보다 최신일 수 있다. 따라서 **외부 main을 내부 작업의 영원한 source of truth로 생각하지 않는다.** 내부 승인된 Git 원본이 기준이 된다.

## 9. 이 기록을 읽는 개발자에게

"왜 Memory Engine을 바로 Hindsight로 만들지 않았는가?" — 원본·권한·재구축 경계를 먼저 검증하고, 여러 엔진을 비교하기 위해서다.

"왜 엔진이 이렇게 단순한가?" — 실사용 가능한 최저 기준선으로 시작하고, 미완성 연구 가설을 공통 데이터 모델에 박아 넣지 않기 위해서다.

"이후의 정확한 구현 순서는 무엇인가?" — **아직 하나로 고정하지 않았다.** 실제 클라이언트 사용, 보안·복구 제약, 메모리 검색 실패, 한국어/코드 도메인 데이터, 비용과 운영 가능성을 확인하면서 결정해야 한다.

"설계를 바꿀 수 있는가?" — 바꿀 수 있다. 다만 원본/기억 경계, 접근·삭제, 출처, 관측 가능한 결과를 해치지 않는지 검토하고, 변경의 근거와 비용을 남겨야 한다.
