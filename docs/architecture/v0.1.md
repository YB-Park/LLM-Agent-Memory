## 1. 비전과 목표

LLM 모델 및 Agent Harness에 종속되지 않는 **개인 소유의 범용 장기 메모리 시스템**을 탐구하고 구축한다.

- GitHub Copilot Agent(VS Code)를 우선 대상으로 하되, Claude Code·Codex 등 **다른 에이전트와 여러 PC/세션**에서도 동일한 원격 메모리를 활용한다.
- 대화·문서·개발 작업 등에서 경험(Experience)을 수집하고, 이를 재사용 가능한 기억(Memory)으로 변환한다.
- 장기적으로 기억의 **연관성, 중요도, 유지 강도, 접근성, 통합, 재구성, 망각·재활성화**를 연구하고 개선한다.
- 처음부터 인간의 기억을 재현하려 하지 않는다. **작은 시스템을 실제 사용하며 측정하고 개선**하는 개발 방식을 따른다.

## 2. 가장 중요한 설계 원칙

1. **Experience ≠ Memory**: 원본 경험과 엔진이 생성한 파생 기억을 분리한다. 기억 표현이나 알고리즘이 바뀌어도 원본이 허용하는 범위 내에서 재처리할 수 있어야 한다.
2. **Engine Independence**: Hindsight, MemoryLACE 또는 자체 메모리 엔진을 실험·교체할 수 있도록 애플리케이션과 엔진의 책임을 분리한다. 초기부터 과도한 범용 플러그인 프레임워크를 구축하지 않는다.
3. **Protocol Independence**: MCP는 에이전트 접근 인터페이스이지 시스템의 핵심이 아니다. HTTP API 등 다른 소비자도 같은 애플리케이션 서비스를 사용한다.
4. **Provenance / Versioning / Rebuildability**: 기억마다 출처와 처리 버전을 추적하고, 재처리·비교·점진적 전환을 가능하게 한다.
5. **Observability**: 어떤 기억이 생성·검색·수정되었는지, 응답에 어떤 근거가 사용되었는지, 비용·지연시간·정확도를 관찰한다.
6. **Security & Deletion**: 하나의 인스턴스에 하나의 신뢰·보안 경계를 둔다. 다른 경계의 데이터는 별도 인스턴스에 둔다. 보존 및 삭제 정책을 구분하고, 원본을 영구 보존한다고 가정하지 않는다.

## 3. 외부 시스템 아키텍처 초안

```text
[VS Code Copilot]  [Claude Code]  [Other Agents / PCs]
         \             |              /
          MCP (remote Streamable HTTP)
                      |
       [Access Layer: MCP + REST + Auth]
                      |
       [Application: Modular Monolith]
       ├─ Experience / Source Management
       ├─ Memory Engine Boundary (Phase 0: Reference Engine)
       ├─ Retrieval Orchestration
       └─ Jobs / Audit / Evaluation
                      |
          +-----------+------------+
          |                        |
     [PostgreSQL]          [Source Storage]
     metadata / state      future optional blobs
     small text sources    (files / S3 compatible)
     relations / jobs
     pgvector (optional later)
          |
     [Background Worker]
     extraction / indexing / reprocessing /
     consolidation / evaluation
```

**초기 배포는 단순하게 유지한다.** 애플리케이션과 Worker는 같은 코드베이스의 별도 프로세스로 실행 가능하게 구성하고, PostgreSQL을 주 저장소로 사용한다. 초기에는 Docker Compose 기반의 단일 원격 서버/VM을 가정한다. 이는 물리적 서비스 분리가 아닌 **논리적 책임 구분**이다.

### 기술 방향 (장기 미확정, Phase 0 기준안은 상세 문서 참조)

| 영역 | 초기 기준안 | 참고 |
| --- | --- | --- |
| 서버 구조 | Modular Monolith | 필요할 때만 서비스 분리 |
| Agent 연결 | Remote MCP, Streamable HTTP | MCP는 얇은 어댑터 |
| 기타 접근 | REST API | 동일 Application Service 재사용 |
| 메타데이터·관계·작업 상태 | PostgreSQL | 저장소 엔진 교체 여지 보존 |
| 의미 검색 | pgvector (옵션) | 초기에는 전문 검색과 병행 검토 |
| 원본 데이터 | **Phase 0: 작은 텍스트는 PostgreSQL** | 대용량·첨부파일에 파일/S3 호환 스토리지 검토 |
| 비동기 처리 | PostgreSQL 기반 Job Queue + Worker | 재시도·멱등성 필수 |
| 운영·배포 | Docker Compose | 초기 개인용 원격 환경 |
| 인증 | 접근 제한 및 개인 인증부터 시작 | 향후 OAuth/다중 사용자 확장 가능 |
| 언어·프레임워크·ORM·LLM | **미정** | 구현 직전에 결정 |

## 4. 책임과 핵심 데이터 영역

- **Source / Experience**: 어떤 에이전트·세션·PC·문서에서 어떤 정보가 들어왔는지. 원본 또는 원본 위치, 수집 시점, 권한, 보존 상태를 관리한다.
- **Memory Artifact**: 메모리 엔진이 생성한 결과물. Narrative/Atomic/Observation/Opinion 등 특정 표현을 공통 데이터 모델로 **성급하게 고정하지 않는다**.
- **Memory Relations / Indexes**: 엔진별 연결·검색 구조. 원본 경험과 구분하여 재생성 가능한 파생 데이터로 취급한다.
- **Processing Run / Jobs**: 엔진·모델·프롬프트·설정 버전, 처리 상태, 실패·재시도와 산출물의 연결을 추적한다.
- **Retrieval / Evaluation Logs**: 질의, 선택된 기억, 근거, 지연시간, 비용, 피드백을 기록한다. 민감정보의 로깅 범위를 제한한다.
- **Principal / 기기 권한**: 각 credential은 한 Principal에 속한다. 읽기·쓰기·관리 권한은 기억 집합 전체에 적용되며 기본값은 모두 미부여다.
- **서버 운영 상태**: 기존 `system_control` 한 행이 활성 Generation, 유지보수 후보, 접수 게이트, 정책·접수 리비전과 복구 격리를 관리한다.

초기 Namespace는 개인·업무·프로젝트 데이터의 접근 권한을 격리하기 위해 도입했다. 단일 사용자가 신뢰 경계를 공유하는 여러 기기로 같은 장기 기억을 쓰는 현재 목표에 맞춰, 격리 단위를 서버 인스턴스로 옮겼다. 프로젝트 A의 경험을 프로젝트 B에서 활용할 수 있으며, 어느 프로젝트·사람·사건·결정·주제에 해당하는지와 어떤 기억을 연결할지는 Memory Engine이 판단한다. 출처·시점·클라이언트 메타데이터를 엔진에 제공한다.

## 5. 우선 설계할 데이터 흐름

### Write (수집·기억 형성)

1. 클라이언트/수집기가 새 Experience를 제출한다. **MCP 연결만으로 모든 대화가 자동 수집되는 것은 아니다.** 실제 수집 범위와 호출 시점은 Harness별로 검증한다.
2. 서버가 Principal의 쓰기 권한과 멱등성 키를 검사하고 원본, 메타데이터, Job, 접수 기록을 함께 커밋한다.
3. Worker가 선택한 Memory Engine으로 처리하고 기억/관계/인덱스를 생성한다. 중복 실행·중단·삭제/권한 변경과 충돌해도 불완전하거나 무효한 결과가 노출되지 않아야 한다.
4. 결과를 버전·출처와 연결하고 정책에 맞는 활성 세대에서 검색 가능 상태로 전환한다. **원본·Job 접수 성공은 기억 생성/검색 가능 성공과 별도**로 클라이언트에 전달한다.

### Read (기억 사용)

1. 에이전트가 MCP 또는 API로 현재 작업의 질의를 전달한다.
2. 읽기 권한이 있으면 Retrieval Engine이 활성 Generation에서 기억을 선택한다.
3. 제한된 토큰 예산 내에 기억·근거·유효성 메타데이터를 반환한다.
4. 에이전트가 검색된 기억을 활용할 수 있다. 서버가 관찰 가능한 것은 **검색·반환 여부**이며, 실제 사용 여부는 클라이언트가 명시적으로 피드백할 때만 기록한다.

### Rebuild (엔진 전환·재처리)

1. 원본 Experience와 Processing Run을 기준으로 **새 엔진/버전**을 별도 실행한다.
2. 기존 기억을 덮어쓰지 않고 새로운 파생 결과를 생성한다.
3. 동일한 질의·시나리오로 품질, 검색 결과, 비용, 지연시간을 비교한다.
4. 평가 후 기억·관계·인덱스가 서로 다른 버전으로 뒤섞이지 않도록 **일관된 활성 세대** 단위로 전환하거나 롤백한다.

## 6. 리뷰 반영: 초기 설계에서 지켜야 할 불변조건

아래는 [Issue #1](https://github.com/YB-Park/LLM-Agent-Memory/issues/1)의 위험 지적을 검토한 결과다. **구현 방법·스키마를 확정한 것이 아니라, 나중에 변경 비용이 큰 실패를 방지하기 위한 최소 계약**이다.

### 권한과 데이터 출처

- **서버가 신뢰하는 인증 주체**를 기준으로 전체 기억 집합에 대한 읽기·쓰기·관리 권한을 확인한다. MCP와 REST 모두 같은 정책을 적용한다.
- 권한은 Source/Experience뿐 아니라 **파생 Memory, 관계, 검색 후보·인덱스, 활성/이전 세대, 로그, 내보내기 및 재처리 결과**에도 적용된다. 검색 후보 선정 단계부터 필터링하고 결과 반환 전에 다시 확인한다.
- 여러 원본을 결합한 기억은 모든 원본의 출처·버전을 추적한다. 서로 다른 신뢰 경계의 원본은 별도 인스턴스에서 운영한다.
- 공통 계층에 필요한 것은 최소한의 **식별자, 출처/버전, 처리 실행/엔진 버전, 생명주기 상태, 엔진별 데이터 참조**다. Narrative/Atomic/Opinion 등 내부 표현은 엔진별로 유지한다. 공통의 거대한 Memory 스키마는 만들지 않는다.

### 삭제와 재노출 방지

- **데이터 삭제** 시 대상 원본과 영향받은 파생 결과를 정책에 따라 즉시 검색·재처리에서 제외하고, 원본·기억·인덱스·관계·캐시·로그 등을 정리한다. `검색 비노출`, `운영 저장소 삭제`, `백업 포함 삭제`는 별개의 보장으로 취급한다.
- **특정 주체(에이전트·기기·토큰)의 접근 철회**는 그 주체의 읽기·쓰기·재처리 권한과 해당 권한으로 진행 중인 작업을 차단하는 것이다. 다른 적법한 주체의 접근까지 일률적으로 차단하거나 공유 데이터를 전역 삭제하지 않는다.
- **Principal의 권한 축소**는 해당 기기의 진행 작업을 fence한다. 다른 기기의 권한과 공유 원본은 유지된다.
- 다중 출처의 기억은 단순히 출처 링크를 제거하지 않는다. 영향받은 파생 기억을 **무효화**하고, 남은 원본으로 재구성할지 결정한다. 이전 세대·롤백 결과에서도 삭제 대상이 되살아나지 않아야 한다.
- Worker가 오래된 권한·원본 상태로 시작했더라도 결과 확정 시 현재 상태를 재검증한다. **상태 재검증과 검색 가능 상태로의 전환 사이에 삭제/권한 변경이 끼어들어 결과가 재노출되는 경쟁 조건을 방지**해야 한다. 이를 위한 트랜잭션 경계, 조건부 버전 확인(CAS), 잠금 등은 상세 설계에서 결정한다.
- 삭제 요청과 결과 확정의 순서를 정의하여 **삭제 완료 이후 과거 처리 결과가 새로 검색 가능해지지 않도록** 한다. 주체별 권한 철회인 경우에는 전역 삭제가 아니라 해당 주체의 접근 차단 기준을 적용한다. 백업 복구 시 삭제·권한 변경 이력을 다시 적용할 방안을 별도로 설계한다.
- 원본 보존 기간과 외부 LLM 제공자에게 보낸 데이터의 취급은 이후 정책으로 정한다. **완전 삭제를 무조건 약속하지 않는다.**

### Write·Worker·복구

- **Experience의 보존·삭제 상태**, **Processing Job의 대기·실행·실패 상태**, **파생 Memory의 유효성**, **Generation/Index의 활성 상태**를 각각 구분한다. 원본이 유효하고 이전 세대는 검색 가능하지만 새 재처리 작업은 실패할 수 있다. 부분 처리 결과를 완성된 기억처럼 노출하지 않는다.
- DB 기록과 Job 등록을 가능한 한 **같은 PostgreSQL 트랜잭션**으로 처리한다. **Phase 0에서는 작은 텍스트 원본도 같은 PostgreSQL 트랜잭션으로 보존**한다. 향후 파일/객체 스토리지를 도입할 때에는 DB와의 분산 트랜잭션을 전제하지 말고 고아 파일·유실 작업의 탐지/복구를 별도 설계한다.
- Job은 중복 실행 가능한 것으로 가정하고 **Principal별 멱등성 키**, 재시도·lease/timeout·영구 실패 처리를 정의한다. **lease가 만료된 이전 Worker의 늦은 결과 확정도 차단**해야 한다. 동일 Job 재실행 시 기억이 중복 공개되면 안 된다(외부 모델 호출의 정확히 한 번 실행을 보장하지는 않는다).
- 원본 저장은 메모리 엔진 처리 실패와 독립적으로 관리한다. 엔진이 실패해도 이미 저장된 유효 경험과 기존 검색 기능을 가능하면 유지한다.

### Rebuild·검색 일관성

- 재처리 결과에는 **원본 집합과 기준 시점, 원본 버전, 엔진/모델/프롬프트/설정 버전, 기억/관계/인덱스 버전**을 연결한다.
- 비교 대상은 격리된 상태로 만들고, 검증 후 **기억과 해당 검색 인덱스가 일치하는 활성 세대**를 전환한다. MVP에서는 쓰기를 잠시 중지하는 **수동 전환**도 허용하되 누락된 요청·미처리 Job이 없음을 검증한다. 무중단 전환과 변경 로그 따라잡기는 추후 필요할 때 도입한다. 롤백 시에도 최신 권한·삭제 정책을 적용한다.
- LLM의 비결정성으로 결과의 완전한 재현을 보장하지는 않는다. 목표는 **입력·설정·결과의 추적 가능성, 재처리 및 비교 가능성**이다.

## 7. 사용·검색·운영 검증 원칙

- **MCP 연결 가능 ≠ 에이전트가 자동으로 기억을 수집/검색함.** Copilot을 우선 클라이언트로 명시적 저장→새 세션 검색→자발적 검색 가능 여부를 실제 버전에서 검증한다. 자동 수집은 별도 Hook/Extension/Importer가 필요할 수 있다.
- 검색 결과는 **근거(Source ID), 시점, 현재 유효성/상태**를 포함할 수 있어야 한다. 부족한 증거는 임의의 확정 사실로 채우지 않는다. 검색된 텍스트·기억은 **지시가 아니라 신뢰할 수 없는 데이터**로 취급한다.
- Phase 0는 **결정론적인 키워드/문자열 검색**과 Reference Engine을 기준선으로 삼는다. 전문 검색·pgvector/임베딩/그래프 탐색은 실제 데이터에서 품질·지연·비용을 비교한 후 도입한다. 한국어·영어 혼용 및 코드 식별자를 평가 집합에 포함한다.
- 관측치는 `retrieved`(검색 후보), `returned`(클라이언트 반환), `client-reported-used`(클라이언트가 사용 보고)로 **구별**한다. 호출 로그에 민감한 원문을 기본 저장한다고 가정하지 않는다.
- 실제 개인·업무 데이터를 넣기 전에 **원격 연결의 인증과 암호화, 기기별 인증정보 폐기, 백업·복구 테스트, 보존·삭제 범위**를 최소한 확정한다.
- 작은 MVP 검증 시나리오: (a) 세션 간 저장/조회, (b) 두 에이전트 간 공유, (c) 출처 역추적, (d) 읽기 전용과 미인가 기기 차단, (e) Worker 중단·재시도, (f) 삭제 후 재노출 방지, (g) 동일 원본의 엔진 버전별 비교 및 롤백, (h) **기기 A만 접근 철회 후 B는 계속 접근 가능**, (i) **Worker의 결과 검증 직후 원본 삭제 → Worker 재개 시 재노출 없음**. 성공 기준과 수치 목표는 테스트 환경을 정하면서 구체화한다.

### 이번 리뷰에서 보류한 결정

- **Ubuntu 20.04 LTS 호환 희망**: [Issue #1](https://github.com/YB-Park/LLM-Agent-Memory/issues/1)과 [Issue #2](https://github.com/YB-Park/LLM-Agent-Memory/issues/2)에 따르면 **별도의 리뷰 대화에서 요청된 신규 요구**다. 이 문서 작성 이전부터 합의한 조건은 아니고, 여기서 실제 호스트 환경이나 런타임 호환성이 검증된 것도 아니다. *리뷰 과정에서 확인된 호환성 희망 요구사항*으로 기록하되, 실제 지원 약속과 최종 배포 대상 확정은 **OS/커널/CPU 아키텍처/Docker·Compose 조합 확인 및 테스트 이후**에 판단한다.
- 다중 사용자 OAuth, S3 이전, Graph DB, 복잡한 세대별 스키마, 정밀한 삭제 SLA, 임베딩 모델, Memory Plugin 프레임워크: **필요성은 인지하되 초기 구현 확정은 보류**한다.
- 중요도, 저장 강도, 접근성, 연상 깊이 제한, 망각·재활성화: 장기 실험 대상이며 이번 인프라 리뷰만으로 알고리즘을 확정하지 않는다.

## 8. 아직 결정하지 않은 것

- 기억의 기본 단위(Narrative vs Atomic), 그래프 구조, 엔터티/관계 갱신 규칙
- Hindsight·MemoryLACE 도입 여부 또는 자체 엔진
- 중요도·유지 강도·접근성, 연결 가중치, 망각·재활성화 알고리즘
- LLM/임베딩 모델 선택, 정밀한 검색·토큰 예산 정책
- Copilot/Claude 등 각 Harness에서 자동 수집이 실제 가능한 범위
- 최종 마이그레이션/물리 스키마 및 인증·백업·복구/배포 환경 실측(Phase 0의 설계 후보와 시험 계획은 상세 문서 참조)

**주의:** Hindsight나 MemoryLACE는 참고 연구이지 채택이 결정된 기술이 아니다. 특히 망각은 향후 핵심 연구 주제이지만 v0.1 구현의 필수 기능이 아니다.

## 9. 다음 LLM/개발자를 위한 핸드오프

이 문서는 **장기적으로 지켜야 할 아키텍처 원칙과 경계**를 설명한다. Phase 0는 [상세 설계 v0.1](../design/phase0-detailed-design-v0.1.md)을 **구현 기준선**으로 채택했고 [구현 추적 이슈 #6](https://github.com/YB-Park/LLM-Agent-Memory/issues/6)에서 P0-0~P0-5를 진행한다. 문서에서 **장기 원칙과 Phase 0에 한정된 선택을 혼동하지 말 것**. 엔진 고유 데이터 구조를 공용 API/저장 스키마에 무리하게 끼워 넣지 말 것.

초기 MVP의 성공 기준은 여러 세션·에이전트에서 동일한 메모리를 조회하고, 출처를 추적하며, 원본이 남아 있는 경우 엔진을 재처리·비교할 수 있는 것이다. 처음부터 모든 종류의 기억 형성, 완성형 그래프, 인간형 망각을 구현할 필요는 없다.
