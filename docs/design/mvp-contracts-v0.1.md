# MVP Contracts v0.1 — 구체화 설계 초안

> **상태: Draft / 논의용 · 2026-11-13**  
> 상위 문서: [Architecture v0.1](../architecture/v0.1.md)  
> 근거 리뷰: [Issue #3](https://github.com/YB-Park/LLM-Agent-Memory/issues/3)  
> **개념적 계약/배경 문서.** 이 문서 자체는 확정 API·DB 스키마가 아니다. **Phase 0의 세부 구현은 [Phase 0 Detailed Design v0.1](phase0-detailed-design-v0.1.md)이 기준선**이며, 이후 구현 증거는 [Issue #6](https://github.com/YB-Park/LLM-Agent-Memory/issues/6)에서 추적한다.

## 1. 무엇을 먼저 검증할 것인가?

- **Phase 0 — 시스템 수직 경로와 제한된 실사용 회상 검증:** 일반 텍스트 Experience 또는 **명시적 기억**을 제출 → 출처 기록 → 비동기 처리 → **Reference Memory Engine**이 원본 투영 또는 명시적 문구 보존 → 별도 세션에서 키워드 기반 검색 → 출처 확인 → 두 버전 결과 비교.
- Reference Engine은 실제 Copilot 명시 저장·회상에 쓸 수 있지만 자동 기억 추출·통합·연상·망각은 수행하지 않는다. 성공의 의미는 **연결·상태·권한·출처·재처리 + 제한된 회상 실용성 검증**이다. 이를 일반적인 장기기억 품질 검증과 혼동하지 않는다.
- **Phase 1 — 더 발전된 기억 형성·검색 실험:** 실제 프로젝트의 소규모 대화/문서 데이터에서 의미 있는 기억 추출·검색과 기본 품질 평가를 진행한다. Hindsight, MemoryLACE 또는 자체 방식의 선택은 별도 설계 결정으로 남긴다.
- 자동 수집, 전용 Graph DB, 고급 망각/중요도, 다중 사용자 OAuth, 대규모 임베딩 및 무중단 자동 전환은 Phase 0에서 **범위 제외**한다. 다만 인증, 권한, 삭제 후 재노출 방지와 같은 불변조건은 제외하지 않는다.

## 2. 논리적 식별자와 생명주기는 분리한다

| 개념 | 독립적으로 추적할 정보(후보) | 상태 예시 · 최종 enum 아님 |
| --- | --- | --- |
| **Source / Experience** | source/experience ID, 원본 버전·출처, 보존 위치/무결성, 접근 범위, 삭제·공개 상태 | 수신 중, 유효·보관 중, 삭제/무효 |
| **Processing Run / Job** | 실행 ID, 원본 집합/버전, 엔진·모델·설정 버전, 실행/재시도·오류 | 대기, 실행 중, 완료, 실패, 취소 |
| **Memory Artifact** | 파생 결과 ID, 원본 참조(다대다 가능), 생성 실행, 범위·유효성, 엔진별 표현 참조 | 준비 중, 유효, 무효 |
| **Generation / Search Index** | 세대 ID, 해당 결과와 인덱스 버전, 활성화 기준 | 준비 중, 검증 완료, 활성, 퇴역 |

**핵심 예시:** Experience E1은 보관·유효 상태일 수 있고, **G1은 검색 가능한 활성 세대**인 동시에 **G2를 생성하는 Job은 실패**할 수 있다. 하나의 Experience `status`로 이 상태들을 모두 표현하지 않는다.

Source(원천)와 Experience(수집 단위)의 관계, 실제 테이블 분할·인덱스 구조는 아직 미정이다. 공통 계층은 출처·권한·실행·생명주기를 추적하되 **Narrative/Atomic/Observation/Opinion의 엔진 고유 표현을 강제하지 않는다**.

## 3. Write — 접수 성공과 기억 생성 성공을 분리한다

### 입력 개념(후보)

원본 또는 참조, 출처 정보, 요청 범위, 멱등성 키. **Phase 0에서는 작은 텍스트만 허용**하고 명시적 기억 의도를 선택적 제출 메타데이터로 표현한다. 파일/외부 blob은 이후 설계 대상이다. **인증 주체와 허용 범위는 서버가 결정**하고 요청 범위는 그 안에서만 적용한다.

### 외부에 약속할 의미

- **Accepted(접수 완료):** 원본이 보존 가능하고 접근 가능한 상태로 확인되었으며, 메타데이터와 처리 Job이 지속적으로 기록된 상태. **아직 Memory가 생성·검색 가능하다는 뜻이 아니다.**
- **Job Completed:** 지정된 실행 결과의 저장과 처리 종료가 확인됨. 해당 결과를 일반 검색에 노출할지 여부는 **활성 세대·권한·유효성 상태**에 따라 별도 결정한다.
- **Failed/Retryable:** 외부 모델 실패, DB 또는 파일 불일치 등을 구분하되, API에서 원본/비밀을 포함한 내부 오류를 그대로 노출하지 않는다.
- 같은 주체/접근 범위와 같은 멱등성 키로 동일 요청을 다시 전송하면 기존 접수 결과를 재사용한다. **동일 키 + 다른 내용**은 조용히 덮어쓰거나 합치지 않고 충돌로 처리하는 방향을 우선 검토한다. 키 유효 기간·중복 제거 단위는 별도 결정한다.

DB 메타데이터와 Job 기록은 같은 일관성 경계에서 확정한다. **Phase 0에서는 작은 텍스트 원본도 PostgreSQL의 같은 트랜잭션에 저장**한다. 파일/객체 저장소 도입은 별도 문제이며 DB와 단일 트랜잭션이라고 가정하지 않는다.

이 문서에는 API 세부 필드를 고정하지 않는다. **Phase 0의 REST/MCP 후보 경로와 응답 예시는 상세 설계 §9에 정의**되어 있으며, MCP/REST는 동일한 Application Service를 호출한다.

## 4. Worker — 오래된 처리 결과를 공개하지 않는다

- Worker의 Job 선점에는 고유한 **유효 소유권/실행 세대(fencing token 등의 방식 후보)**가 필요하다. lease 만료 후 Worker B가 인계받았다면 늦게 끝난 Worker A의 결과가 B의 결과를 덮거나 중복 공개하지 않아야 한다.
- LLM 등 긴 외부 작업 동안 DB 트랜잭션·락을 지속해서 붙잡아두는 설계는 피한다. **결과 확정 시점에 현재 Job 소유권과 출처 상태/권한 버전을 일관되게 검증**하는 계약을 둔다.
- 원본 삭제 또는 범위 변경과 결과 공개가 경쟁하면, **삭제/변경이 완료된 뒤 기존 권한/원본으로 생성된 결과가 새로 공개되면 안 된다.** 검사와 공개 사이의 경쟁을 막는 구체적인 원자성 메커니즘(CAS/버전 비교/잠금/트랜잭션 등)은 구현 설계에서 선택한다.
- Job 중복 실행 자체와 외부 모델 중복 호출은 가능하다. 목표는 **중복 공개·데이터 오염 방지**이지 외부 LLM 호출의 정확히 한 번 실행 보장이 아니다. 비용의 중복 발생 가능성은 기록한다.
- 별도 검증 시나리오: 결과 저장 직후 프로세스 종료, lease 만료 A/B 경쟁, 재시도, 결과 확정 직전 원본 삭제, 특정 기기 인증 철회.

## 5. Read — 결과의 의미와 근거를 함께 제공한다

- 입력 개념: 질의, 요청 범위, 결과 수 또는 토큰 예산. **실제 권한 범위는 서버에서 교집합으로 강제**한다.
- 결과 개념: **원본/파생 기억 구분**, 내용 또는 발췌, 출처 ID와 가능한 위치·시점, 유효성/활성 세대 또는 처리 버전, 검색 근거를 식별할 정보.
- 결과 없음, 관련 Job이 아직 처리 중임, 검색 실패는 내부적으로 구분한다. **권한 없는 데이터의 존재를 응답·오류·개수로 유추할 수 없도록** 외부 노출 수준을 정한다.
- 원본 자체를 검색 대상으로 허용할지는 미정이다. 허용하는 경우 *원본 검색*과 *Memory 검색*을 혼동하지 않으며, 권한·삭제 기준을 동일하게 적용한다.
- 단순 키워드/전문 검색을 기준선으로 두고, **한국어/영어 혼용과 코드 심볼 검색**을 작은 실사용 질의로 테스트한다. FTS가 한국어에서 충분할 것이라고 가정하지 않는다.
- 서버 측 로그는 `retrieved`(후보), `returned`(실제 반환), `client-reported-used`(클라이언트 피드백)를 구분한다. **실제 에이전트의 답변 활용은 피드백 없이 확정하지 않는다.**
- 검색 결과와 원문에 포함된 텍스트는 LLM/에이전트에 전달할 때 **신뢰할 수 없는 데이터**이며 상위 지시나 도구 권한을 대체하지 않는다.

## 6. Rebuild — 처음에는 비교 가능성과 안전한 수동 전환부터

- 새 처리 버전은 기존 활성 결과를 덮어쓰지 않고 **격리된 Generation**으로 만든다. 기준 원본 집합·버전과 처리 설정을 기록한다.
- 기억과 인덱스는 **같은 세대**로 조회되어야 한다. 전환/롤백 시 삭제·권한 철회의 *최신 상태*가 이전 세대에도 적용되어야 한다.
- **Phase 0에서는 쓰기를 잠시 중지하고 수동 전환하는 방식도 허용**한다. 이 경우 중지 시점과 처리 대기 요청의 정책, 대상 기준 집합, 미처리 항목이 없는지 확인하는 절차를 기록해야 한다.
- 무중단 전환을 필요로 할 때에만 신규 경험의 변경 로그·따라잡기(replay/catch-up)와 원자적 전환을 추가 검토한다. 타임스탬프만으로 누락 없는 순서를 보장한다고 가정하지 않는다.
- 롤백은 *메모리 엔진이 작성한 결과의 이전 버전*으로 돌아가는 것이지, **삭제/권한 변경을 과거로 되돌리는 동작이 아니다.**
- 외부 LLM의 비결정성을 인정한다. **완전 동일한 결과 재생산보다 재처리·비교·출처 추적 가능성**을 우선한다.

## 7. 클라이언트 및 운영 검증

- 최초 대상은 **VS Code Copilot Agent**다. Remote MCP가 연결된다는 것만으로 자동 수집·회상이 동작하는 것은 아니므로, 명시적 저장 → 새 세션 검색 → 다른 에이전트에서 공유 → 자발적 검색 여부를 **분리해서** 검증한다.
- Ubuntu 20.04 호환 희망은 리뷰 과정에서 전달된 요구사항이지만 지원/동작 검증은 아직 아니다. OS, 아키텍처, 커널, Docker·Compose 런타임 조합을 기록하고 실제 시험으로 판단한다. 우선 개인용 단일 서버를 상정하되 배포 기술은 잠정안이다.
- 실제 개인·업무 데이터를 넣기 전에는 원격 인증/암호화, 기기별 접근 철회, 백업과 별도 환경 복구, 삭제 및 로그 보존 정책을 확인한다.
- 최소 실패 테스트: (1) A 인증 철회 후 B 접근 유지, (2) 원본 삭제 후 어느 세대에서도 재노출 없음, (3) 재검증 직후 삭제와 공개 경쟁, (4) **Phase 0의 DB 원본/receipt/Job 원자성 및 중복 응답 복구**, (5) Worker lease 만료 A/B 경쟁, (6) G1/G2 비교 및 롤백, (7) 명시적 기억의 수동 삭제·정정. 파일/DB 간 장애는 파일 저장 도입 시 검증한다.
- Phase 1에서는 질의별 기대 기억·무관한 기억·접근 금지 기억을 포함한 소규모 평가 집합으로 정확도, 지연, 모델 비용을 비교한다.

## 8. 아직 확정하지 않을 사항

- API 경로, 응답 JSON, HTTP 코드, MCP 도구 이름, 언어/프레임워크/ORM 및 세부 DB 스키마
- Source·Experience 실제 물리적 테이블 분리, 구체적인 Worker Queue/lease 메커니즘
- 인증 방식, 상세 ACL, 백업 삭제 SLA 및 지원 OS/런타임 매트릭스
- 원본을 검색 대상으로 제공하는 정책, 임베딩 모델·Graph DB 여부
- Hindsight·MemoryLACE 채택 여부, 기억의 단위/통합/연상·중요도·접근성·망각 알고리즘
- Generation 자동 전환, 변경 로그 재생, 고급 무중단 운영

**진행 현황:** 대표 시퀀스, 내부 인터페이스, PostgreSQL 스키마 후보, Reference Engine, 실패 조건은 [상세 설계 v0.1](phase0-detailed-design-v0.1.md)에서 구체화되었다. 현재 단계는 **구현 착수 및 실제 환경/장애 검증**이며, [Issue #6](https://github.com/YB-Park/LLM-Agent-Memory/issues/6)을 따라 진행한다. `evidence_refs` 강한 근거 연결·자동 정정·기억 통합은 Phase 0 범위 밖이다.
