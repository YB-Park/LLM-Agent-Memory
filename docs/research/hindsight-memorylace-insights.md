# Hindsight · MemoryLACE 조사와 우리 프로젝트의 인사이트

> **문서 목적:** 외부 자료를 볼 수 없는 환경에서도 왜 이 연구들을 참고했는지 알 수 있도록 **논문이 제안한 구조**, **우리가 받아들인 통찰**, **아직 선택하지 않은 구현 방식**을 나눠 기록한다. 2026-11-16 시점의 자료와 프로젝트 대화/리뷰를 근거로 작성. **특정 논문/코드 채택 결정이나 복제 구현 명세가 아니다.**
>
> 논문에 설명된 구조/성능은 논문 저자들의 주장과 해당 평가 조건의 결과이며, **우리 프로젝트에서 재현하거나 직접 실측한 값이 아니다.** 이 메모는 원문을 대체하는 완전한 논문 재현이 아니라 설계 의사결정에 필요한 맥락을 보존하기 위한 해설이다.

## 1. 무엇이 문제라고 보았는가

긴 대화 기록을 계속 덧붙이거나 검색 결과 top-k를 프롬프트에 넣는 방법만으로는 장기 기억 문제가 끝나지 않는다.

- **증거와 해석이 섞인다.** 사용자가 직접 말한 것, 에이전트가 요약·추정한 것, 반복적으로 관찰된 패턴, 에이전트의 주관적 의견이 모두 같은 "fact"로 취급되기 쉽다.
- **시간에 따른 변화가 흐려진다.** 당시에는 맞았지만 지금은 바뀐 결정, 새 증거가 옛 주장을 대체한 경우, 서로 모순되는 주장, 단순 반복을 구별하기 어렵다.
- **회상은 보존과 다르다.** 데이터가 남아 있어도 질문의 표현·시간·문맥이 달라지면 관련 기억을 찾지 못할 수 있다.
- **기억의 양과 품질 사이에 비용이 있다.** 추출·요약·관계 구축·매번 전체 재평가·다단계 검색은 비용·지연·오류 가능성을 증가시킨다.
- **근거가 끊기면 통제하기 어렵다.** 파생 기억이 원문·시점·접근 정책과 떨어지면 정정과 삭제/복구가 어려워진다.

Hindsight는 특히 **사실/경험/요약/의견을 구별한 구조적 기억과 추론**, MemoryLACE는 **현재/과거/반복/대체/모순을 다루는 국소적 생명주기**를 강조한다. 두 방향은 경쟁 관계이기도 하지만 서로 배타적이라는 결론을 내린 것은 아니다.

## 2. Hindsight에서 확인한 내용 (논문·시스템의 설명)

**참고 자료**

- 원 논문: [Hindsight is 20/20: Building Agent Memory that Retains, Recalls, and Reflects — arXiv 2512.12818](https://arxiv.org/abs/2512.12818), [본문 HTML](https://arxiv.org/html/2512.12818v1)
- [Hindsight: Structured Agent Memory that Retains, Recalls, and Reflects — ACL 2026 System Demonstration](https://aclanthology.org/2026.acl-demo.27/)
- 공개 구현: [vectorize-io/hindsight](https://github.com/vectorize-io/hindsight)

### 2.1 네 가지 논리적 기억 영역

| 영역 | 논문이 구분하려는 내용 | 우리 프로젝트에 주는 통찰 |
| --- | --- | --- |
| **World** | 외부 세계의 사실·사건·관계 | 사실의 근거와 유효 시점을 추적할 이유 |
| **Experience** | 에이전트 자신의 행동·경험에 관한 기술 | "무엇을 했다"와 "세계가 그렇다"를 구분할 이유 |
| **Observation** | 여러 근거에서 종합한 대상/엔터티의 비교적 중립적인 프로필 | 요약은 원증거와 다른 **파생 산출물**이라는 점 |
| **Opinion** | 시간과 신뢰도를 가진 에이전트의 주관적 판단 | 의견/추정/선호를 객관적 사실로 승격시키지 말아야 함 |

위 구분이 **유일한 정답이라는 결론은 아니다.** 특히 이 논문의 Experience Network는 우리 저장소의 원천 입력 단위인 Experience와 이름만 같고 책임이 다르다.

### 2.2 세 가지 핵심 동작

**Retain**: 입력 대화/문서에서 시간을 고려한 narrative fact를 추출하고 엔터티를 식별·연결해 기억 구조를 구축한다. 단순 문자열 복사를 넘어 맥락을 보존한 서술 단위를 선택한다.

**Recall**: 벡터 유사도, 키워드, 그래프 확장, 시간 조건 등 서로 다른 검색 경로로 후보를 찾아 합치고 재정렬한 후 토큰 예산 안에 결과를 담는다. 논문은 다중 전략과 점수 결합/재순위화를 제시한다.

**Reflect**: 회상한 근거를 이용해 더 긴 추론을 수행하고, 경우에 따라 에이전트의 의견·신뢰도를 형성하거나 갱신한다. 이때 단순 검색과 **증거에 기반한 추론/믿음의 변화**를 구분한다.

### 2.3 우리가 얻은 인사이트

1. **파생 기억의 종류를 구분할 필요**가 있다는 점. 단순 원문 발췌, 요약, 사실 추출, 엔터티 관찰, 의견을 모두 동등한 원본 사실로 반환하면 오해가 생긴다.
2. **Narrative 단위는 맥락을 살릴 수 있다**는 점. 너무 잘게 쪼갠 atomic fact는 결정 이유·조건·예외·대화 흐름을 잃을 수 있다. 반대로 narrative가 길면 검색·중복 처리에 비용이 든다. 어느 쪽이 적합한지는 데이터로 확인한다.
3. **기억 검색은 단순 유사도 한 가지로 해결되지 않을 수 있다**는 점. 코드 식별자는 lexical, 자연어 표현은 semantic, "언제부터 바뀌었는가"는 temporal, 간접 연결은 graph/hop이 강할 수 있다.
4. **왜 그런 답을 했는지를 추적**하려면 원출처와 파생 단계가 연결돼야 한다는 점. 결과를 근거 없이 합치거나 믿음으로 고정하지 않는다.
5. **관찰 요약과 의견 생성의 갱신 비용**을 무시하면 안 된다는 점. 변화가 발생할 때 모든 엔터티·기억을 재평가하는 구조가 과도할 수 있다.

### 2.4 지금 채택하지 않은 것

- 네 영역을 모두 **물리적 DB 스키마나 공통 API의 enum**으로 고정.
- Hindsight의 모든 graph edge, entity resolver, confidence-update 규칙 또는 behavioral disposition을 그대로 구현.
- 네 종류 검색 파이프라인을 무조건 병렬 실행하고 동일한 fusion/reranker를 사용.
- 성능 수치를 우리 제품에도 재현된 결과로 간주.

## 3. MemoryLACE에서 확인한 내용 (논문이 제안하는 내용)

**참고 자료**

- [MemoryLACE: Memory Lifecycle-Aware Consolidation and Evidence Retrieval — arXiv 2609.03201](https://arxiv.org/abs/2609.03201) (2026-09-02 제출)
- [논문 개요 및 원문 연결 — alphaXiv](https://www.alphaxiv.org/abs/2609.03201)

### 3.1 기본 단위와 관계

MemoryLACE는 **출처가 있는 원자적 자연어 기억(atomic natural-language memory)**을 유지하면서, 변화의 생명주기를 **희소한 관계**로 명시적으로 표현한다. 넓은 지식 그래프 전체를 유지하는 대신 관련된 증거 사이의 국소 관계를 활용한다.

논문에서 주요하게 다루는 관계는 다음과 같다.

- **Merge / 반복 근거:** 표현이 달라도 실질적으로 같은 정보를 반복하거나 서로 뒷받침하는 경우를 연결한다. 중복 원문을 한쪽이 무조건 덮어써야 한다는 뜻은 아니다.
- **Supersession / 대체:** 새로운 정보가 옛 내용을 갱신한 경우 새 정보와 과거 상태의 관계를 추적한다. 과거 상태는 역사적 질문의 증거로 남을 수 있다.
- **Contradiction / 모순:** 동시에 참이라고 보기 어려운 진술이 있다는 사실을 관계로 남긴다. 모순을 자동으로 둘 중 하나로 "해결"했다고 주장하지 않는다.

검색에서는 각 메모리를 독립된 문자열 하나로 반환하는 대신 **현재, 과거, 지지, 충돌 증거의 맥락을 복원**해 downstream 모델이 판단하도록 한다. 논문은 시간 정보와 관계 확장이 효과에 기여한다고 보고한다. BEAM 비교에서 Hindsight 대비 end-to-end 실행 시간이 줄었다는 결과도 보고하지만, **평가 환경·구현/모델·질의 유형이 다른 시스템의 보편적 우열을 뜻하지 않는다.**

### 3.2 우리가 얻은 인사이트

1. **기억의 최신성은 단순한 생성시각 내림차순이 아니다.** 새 정보가 과거 정보를 대체했는지, 예외인지, 단지 다른 시점의 관측인지가 중요하다.
2. **'모순을 찾아 표시'와 '모순을 해결'은 다른 작업이다.** 특히 개발 결정이 바뀌었을 때 과거 결정을 지워 버리면 "왜 바뀌었나"라는 질문에 답하기 어려워진다.
3. **중복 통합은 정보 손실을 낳을 수 있다.** 반복된 관측 자체도 신뢰의 증거이거나 다른 출처에서 독립적으로 확인된 증거일 수 있다.
4. **국소적/희소한 링크와 필요한 시점의 증거 확장**만으로도 가치가 있을 수 있다. 그래프 전체를 구축·갱신해야 한다고 미리 가정하지 않는다.
5. **원자적 기억과 큰 문맥을 함께 다룰 수 있어야 한다**는 점. 아주 작은 단위의 정확한 비교에는 이득이 있으나 이유·조건·연속된 맥락이 손상될 수 있으므로 원본과 주변 증거에 돌아갈 경로가 필요하다.

### 3.3 지금 채택하지 않은 것

- MemoryLACE의 atomic schema와 활성/비활성 상태를 모든 엔진에 강제.
- Merge·Supersession·Contradiction 분류에 특정 LLM·임계값·프롬프트를 선제 선택.
- 기억의 대체를 곧 법적/정책상 데이터 삭제라고 해석.
- 국소 링크만 있으면 모든 장기기억 질의가 해결된다는 가정.

## 4. 두 연구의 비교와 우리의 선택

| 관점 | Hindsight의 강조점 | MemoryLACE의 강조점 | 우리에게 남은 질문 |
| --- | --- | --- | --- |
| 기억 표현 | Narrative, 사실·경험·관찰·의견의 구분 | 출처 있는 Atomic 기억과 생명주기 관계 | 맥락 보존과 국소 갱신의 최적 균형은? |
| 연결 구조 | 시간·엔터티·의미·원인 관계와 그래프 검색 | 희소 merge/supersession/contradiction | 둘 중 어느 구조가 실제 개발 대화에 충분한가? |
| 갱신 | Observation/Opinion 갱신과 Reflection | 새 증거와 관계를 국소적으로 업데이트 | 새 사실 유입 시 갱신 범위를 얼마나 좁힐 수 있나? |
| Retrieval | 키워드·벡터·그래프·시간 검색의 결합 | 관계를 포함한 evidence unit 재구성 | 어떤 질의에 어떤 경로를 언제 쓸까? |
| 비용 | 구조와 추론이 풍부하지만 작업이 많음 | 국소 관계로 비용과 복잡도를 줄이려는 접근 | 성능 이득 대비 인덱싱/모델/지연 비용은? |
| 설명 가능성 | 사실·관찰·의견·출처/신뢰 구분 | 현재·과거·모순·근거 구분 | 사용자에게 불확실성과 시점·근거를 어떻게 표현하나? |

**우리의 선택은 Hindsight와 MemoryLACE를 동일한 인터페이스 뒤에 즉시 꽂아 넣는 범용 플러그인 프레임워크가 아니다.** 원본 Experience/권한/처리 이력을 안정적으로 유지하고, 두 번째 연구 엔진을 실제로 시도할 때 무엇을 공통화할지 결정하는 것이다.

참고한 기존 시스템으로는 Letta/MemGPT의 **컨텍스트 계층 관리**, Zep/Graphiti의 **시간적 관계/그래프** 등이 있었지만, 이 문서에서는 심층 도입 평가를 하지 않았다. 이들을 현재 후보 중 우선순위 1위로 결정하지도 않았다.

## 5. 우리가 별도로 논의한 '망각'과 '회상' 가설

이 부분은 **논문의 확정된 구현안이 아니라, 프로젝트에서 탐구하고 싶어 했던 방향**이다.

### 5.1 기억 강도 vs 검색 접근성

한 기억을 오래 보존해야 한다는 것과 지금의 질의에서 쉽게 접근할 수 있다는 것은 다르다.

- **지속성/보존:** 그 기억의 원본·근거 또는 요약을 얼마나 남겨둘지.
- **접근성/활성:** 평범한 질문에서 얼마나 쉽게 후보로 떠오를지.
- **심층 재활성화:** 평소에는 거의 보이지 않지만 깊은 검색·연상·반복 단서에서 다시 찾을지.

데이터 삭제는 별도의 거버넌스 정책이므로 이 개념들의 점수가 낮다고 원본을 자동 삭제하지 않는다. 재활성화를 보장하는 구체 알고리즘은 미결정이다.

### 5.2 중요도, 반복, 최근성, 유효성, 사용

향후 고려한 신호에는 최근성, 명시적 중요도, 반복 독립 증거, 실제 검색·사용, 특정 프로젝트의 현재성, 충돌·변경 상태 등이 있다. **어느 신호에 얼마나 가중치를 둘지**, 서버가 실사용 여부를 얼마나 관측할 수 있는지, 점수의 시간이동이 바람직한지는 미결정이다.

조회 횟수의 증가를 곧 "중요한 기억"이라고 단정하면 인기 편향/자기 강화가 발생할 수 있다. 검색에서 노출되지 않은 기억은 사용 기회를 잃어 더 묻히는 문제도 고려해야 한다.

### 5.3 제한된 통합·연결 탐색

새로 들어온 매 경험을 전체 기억과 완전 비교/통합하지 않고 **관련 후보 집합 안에서만** 업데이트하는 방식, 검색시 **bounded hop/depth**로 연결을 확장하는 방식은 매력적인 실험 가설이다. 하지만 경계가 너무 작으면 멀리 있는 관계를 못 찾고, 너무 크면 비용/잡음이 늘어난다. 범위·중단조건·연결 가중치 공식은 정하지 않았다.

### 5.4 '잊힘'을 측정하려면 무엇을 봐야 할까

- 원본이 존재하지만 현재 인덱스에는 검색되지 않는가?
- 검색 후보에는 있으나 top-N/토큰 예산에서 제외됐는가?
- 에이전트가 결과를 받았지만 사용하지 않았는가?
- 실제로 저장 정책에 의해 삭제·무효화됐는가?

이 네 결과는 완전히 다른 문제다. 망각 연구는 원본·파생 데이터·인덱스·에이전트 행동의 어느 층을 다루는지 선언해야 한다.

## 6. 구체 연구를 시작하기 전의 질문

1. 개발 대화의 **결정과 그 이유**, 코드 제약, 임시 가설, 변경 이력을 어느 단위로 추출하면 가장 덜 왜곡되는가?
2. 같은 사실을 여러 세션에서 반복했을 때 중복 제거가 필요한가, 지지 근거를 유지해야 하는가?
3. 사용자의 진술·에이전트 추정·코드에서 확인한 사실을 어떤 검증 수준으로 표시할까?
4. 변경된 결정은 이전 사실을 "잘못된 것"으로 만들까, 아니면 "그 시점에 유효했던 것"으로 남길까?
5. 한영 혼용/코드·식별자/짧은 프로젝트 명칭에서 lexical, semantic, temporal 검색을 어떻게 결합할까?
6. 하나의 인과 관계를 graph hop 없이 찾을 수 있나? 관계 확장의 비용·오탐은?
7. 무엇을 유지할지와 무엇을 자주 회상할지를 분리할 이유가 실제 데이터에서 보이나?
8. 자동 통합·망각이 설명 가능성과 삭제/권한 불변조건을 훼손하지 않는가?
9. 원본만으로 Rebuild 가능한 엔진과, 과거 사용·상태·시간 변화 이벤트가 필요한 엔진의 차이를 어떻게 다룰까?
10. 에이전트가 검색 도구를 호출하지 않는 실패와 엔진의 recall miss를 어떻게 구분할까?

**질문에 대한 특정 해답, 점수식, graph schema 또는 모델 프롬프트를 미리 확정하지 않는다.** [연구 질문과 평가 관점](future-experiments-and-questions.md)에 비교 접근법을 정리했다.

## 7. 성능 수치에 대한 주의

논문의 benchmark 정확도와 지연 수치는 각 연구자가 설정한 task, baseline, 모델, 검색 구현 및 하드웨어 조건에 영향을 받는다. 다른 논문의 절대 수치를 나란히 놓아 "우리 목적에 우수"라고 판단할 수 없다. 우리 기준선은 Phase 0 Reference Engine이고, 같은 원본/질문/접근 정책에서 재현 가능한 비교가 먼저 필요하다.

장기기억의 QA 정확도만 최적화하면 **출처 누락, 오래된 사실 확신, 민감 데이터 누출, 삭제 후 재노출**을 놓칠 수 있다. 품질 평가에는 근거·시간·거절/불확실성, 지연·비용, 수정·삭제 안전성까지 포함시킬 가치가 있다.
