# Phase 0 이후의 연구 질문과 평가 관점 — 확정 로드맵이 아닌 연구 지도

> 이 문서는 기능 목록/개발 명령이 아니라, 프로젝트에서 **왜 다음 실험을 할 수 있는지**, **어떤 실패가 발견되면 무엇을 비교하면 좋을지**, **무엇을 아직 모르는지**를 보존한다. 순서·알고리즘·가중치·기술을 확정하지 않는다. 사내망에서 생기는 새로운 관측이 이 목록보다 우선한다.

## 1. 연구 접근법

Phase 0 Reference Memory Engine은 단순한 Mock이 아니라 **가장 낮은 비용의 실사용 기준선**이다. 여기에 고급 추출, 연결, 통합, 망각을 추가할 이유는 **실제 질문이 실패하고 원인이 드러났을 때** 더 분명해진다.

기억 서버를 개선할 때는 다음 문제를 섞지 말고 구분한다.

1. **수집:** 보존할 Experience가 아예 들어오지 않았다.
2. **가공:** Experience가 있지만 유용한 기억 Artifact를 만들지 못했다.
3. **검색:** 기억은 존재하지만 질의와 연결되지 않거나 순위 밖에 있다.
4. **전달:** 검색 후보는 있었지만 결과 예산/권한/전송 문제로 전달되지 않았다.
5. **사용:** 에이전트가 도구를 호출하지 않았거나 반환된 결과를 답변에 사용하지 않았다.
6. **현재성·진실성:** 옛 기억/오해/모순을 지금도 맞는 사실로 취급했다.
7. **정책·운영:** 접근 정책, 삭제, 원본 복구/재처리의 정합성이 깨졌다.

"회상이 안 됐다"는 표현만으로는 1~7 중 어디를 개선해야 할지 알 수 없다.

## 2. 기억 형성: 무엇을 기억으로 만들까

**질문:** 개발 대화·문서·Agent 실행 기록에서 어떤 내용을 남기면 나중에 도움이 되는가?

검토했던 가능성:
- 사용자 명시 결정/선호/주의사항을 그대로 보존하는 가장 낮은 위험의 경로.
- 이유·조건·예외를 함께 담는 **Narrative** 기반 추출.
- 반복·대체·모순의 비교가 쉬운 **Atomic** 기반 추출.
- 사건/결정 및 근거를 연결하되 필요할 때만 요약하는 **혼합형** 표현.
- 코드, 설계 문서, 실제 테스트 결과와 사용자의 주장 사이의 출처·검증 차이.

**관측 포인트:** 정확한 결정 내용/이유 복원, 조건 누락, 주체 오인, 설명 가능한 출처, 추출 지연/비용, 잘못된 확신의 비율. 원본이 지워지거나 접근 범위가 바뀔 때 다시 가공할 수 있는지도 중요하다.

**미결정:** 기억의 최소 단위, 추출 알고리즘/모델, 단위별 최대 길이, 엔터티 정규화와 버전 처리 방식.

## 3. 기억의 갱신과 통합: 바뀌는 정보를 어떻게 다룰까

**질문:** 새 경험이 이전 기억을 반복/보강/업데이트/반박하는지 판별할 수 있는가?

검토했던 가능성:
- 단순 중복 제거 vs **독립적인 반복 증거 보존**.
- 기존 내용이 무효인지, **그때는 유효했던 역사적 상태**인지 구분.
- 변경된 사실의 대체 관계(Supersession)와 현재·과거 시점 구분.
- 아직 정리되지 않은 모순을 **해결된 사실로 덮지 않고 함께 표시**.
- 변경 대상과 가까운 관련 기억만 업데이트하는 **bounded/local consolidation**.

**관측 포인트:** 현재/과거 질의의 구분 성공률, 모순 검출의 오탐/미탐, 과도한 merge로 사라진 정보, 출처 유실, 한 입력 처리 비용/범위.

**미결정:** 업데이트를 어떤 엔티티/사실 기준으로 묶을지, 신뢰 우선순위/승인/충돌 해결 절차, 관계형 DB vs sparse graph vs 전체 그래프의 경계.

## 4. 검색: 기억이 남아 있는데 못 찾는 문제

**질문:** 어떤 상황에서 lexical 검색, 의미 검색, 시간 조건, 연결 관계 확장이 실질적으로 도움이 되는가?

검토했던 가능성:
- Phase 0의 다중 키워드/힌트 검색과 원문 구간 투영.
- 한국어 조사·동의어·형태변화, 영어 기술 용어와 코드 식별자에 대한 lexical 개선.
- 의미 검색 + 재순위화(인덱스 버전과 모델/차원 추적을 전제로).
- 시간 질문과 변경/수정 이력에 대한 temporal 검색.
- 단일 검색 결과에서 연관된 결정 이유를 찾아가는 제한된 multi-hop/graph 확장.
- 짧은 답이 가능한 조회와 여러 근거를 읽어야 하는 **deep recall/reflect** 구분.

**관측 포인트:** 필요한 기억의 후보 진입/반환/에이전트 사용 여부, top-N 및 토큰 예산에 따른 누락, 근거 신뢰/현재성, 무관한 기억 반환, 지연·비용, 권한/프로젝트 누출 0.

**미결정:** 임베딩/검색 엔진, 혼합 검색 비중, 재순위화, graph hop 수, 토큰 예산, 검색 실패 시 재시도 전략.

## 5. 기억의 강도·접근성·망각·재활성화

**질문:** 오랫동안 보존할 가치와 지금 쉽게 회상될 가치는 같은가? 오래된 기억을 완전히 버리지 않고 필요할 때 되살릴 수 있는가?

논의한 연구 가능성:
- **보존/지속성:** 실제 원본 또는 요약이 얼마나 오래 관리되는가.
- **접근성:** 평범한 검색에서 우선 떠오를 가능성.
- **활동/반복:** 사용·조회가 도움이 되는 신호인지, 노출 편향인지.
- **시간:** 새로운 정보가 왜 오래된 정보를 잠시 밀어내는지.
- **상황 적합성:** 프로젝트·작업·질문의 맥락이 달라졌을 때 접근성이 바뀌는지.
- **재활성화:** 직접적인 단서나 깊은 검색으로 이전에 거의 검색되지 않던 기억을 다시 찾을 수 있는지.

**절대로 혼동하지 않을 것:** 자동 '망각'을 서버의 데이터 삭제/비공개 정책과 동일시하지 않는다. 보존이 허용된 경험만 재활성화할 수 있고, 이미 삭제·권한 철회된 데이터는 접근성 점수가 높아도 반환하면 안 된다.

**미결정:** 망각 곡선, 강도·접근성의 수학적 모델, 시간 감쇠, 사용 피드백의 신뢰도, deep search 트리거, 원본/요약/인덱스 보존의 정책적 경계. **연구 가설이지 Phase 1 필수 명세가 아니다.**

## 6. 단위와 상태의 독립성: 엔진 교체를 실제로 시험하려면

Phase 0에서는 reference/1(전체 투영)과 reference/2(문단 투영)를 같은 원본으로 재처리한다. 이는 **서비스의 결과/인덱스 교체 경로**를 검증했지만, Hindsight의 다중 네트워크나 MemoryLACE의 lifecycle 그래프가 쉽게 대체된다는 증명은 아니다.

나중에 완전히 다른 엔진을 시도할 때 새로 발견할 질문:
- 그 엔진의 기억은 독립적인 문장인가, 그래프 상태/요약/의견의 집합인가?
- 원본 입력 하나만 처리하면 되는가, **여러 Experience의 연결과 과거 엔진 상태**가 필요한가?
- 이전 데이터/권한·삭제/생명주기 정책을 어떤 최소 메타데이터로 전파할까?
- 엔진 결과를 비교하고 안전하게 전환하는 단위가 지금의 Generation으로 충분한가?
- 기존 검색·MCP 도구의 외부 계약을 바꾸지 않고 engine-specific 정보를 어떻게 표현할까?
- LLM의 비결정적 처리 결과를 **완전 재현**할 수는 없다면, 무엇을 versioning·audit·snapshot해야 검증 가능한가?

**결론을 미리 만들지 말자.** 실제로 다른 내부 모델을 다루는 두 번째 엔진을 도입할 때 공통 인터페이스가 과도한지/부족한지 판단한다.

## 7. 평가 데이터에 담아두면 좋은 질문 종류

다음은 **예시 평가 범주**다. 실제 사내 프로젝트 내용이나 질문을 이 외부 문서에 채우지 않는다.

| 범주 | 예시 질문 의도 | 구별해야 할 오류 |
| --- | --- | --- |
| 단순 사실 | "어떤 DB를 선택했었지?" | 저장/조회 실패, 기본 키워드 miss |
| 이유·조건 | "왜 그 구조로 결정했지?" | 원자화/요약에서 맥락 소실 |
| 시간·변경 | "지난달에는 무엇을 쓰기로 했고 지금은?" | 과거/현재 상태 혼동 |
| 모순·불확실성 | "두 사람이 다른 결정을 기록했는데?" | 거짓 단정, 미해결 모순 은폐 |
| 여러 세션 | "앞선 세 번의 논의 결론은?" | 범위 누락, 잘못된 병합 |
| 한영·코드 | "PostgreSQL, foo_bar, C++" | 토크나이저·질의 정규화 문제 |
| 무관하거나 근거 없음 | "그런 결정을 내린 적 있어?" | 거짓 기억과 근거 없는 확신 |
| 범위·삭제 | "다른 프로젝트의 비공개 결정" | 유출, 철회/삭제 후 재노출 |
| 자발적 회상 | 사용자가 도구 호출을 지시하지 않음 | Harness 미호출 vs 검색 미스 |
| 재처리·전환 | 같은 경험을 두 엔진으로 조회 | 색인 혼합, 삭제 재노출, 비용 비교 |

한 질문에 **기대하는 출처·시점·허용 범위·어떤 답은 거부해야 하는가**를 함께 기록하면 단순 string-match보다 유용하다.

## 8. 평가 결과에서 지켜야 할 구분

- **Retrieval candidate / Returned / Client-reported used**: 서버가 관찰한 것과 에이전트 행동을 분리한다.
- **관련성 vs 현재성 vs 근거 정확성**: 비슷한 문장이더라도 최신 결정을 잘못 답하면 실패다.
- **Recall vs precision vs abstention**: 정답을 찾는 능력과 잘못된 답을 하지 않는 능력을 나눠 본다.
- **Latency·compute·storage·LLM calls**: 성능이 좋아졌어도 자원 비용이 과도한지 확인한다.
- **Access/deletion invariant**: 검색 성능을 올리더라도 다른 권한/삭제 정보를 누출하면 실패다.
- **Comparison reproducibility**: 원본 집합·질의·처리 버전·환경·시간·설정 차이를 기록한다. 비결정적 엔진의 출력 byte 동일성을 강제하지 않는다.

외부 연구의 benchmark 수치는 탐색의 참고이지 내부 운영에 대한 증명은 아니다. 각 실험은 같은 질문/데이터/허용 범위에서 Reference Engine과 비교하는 것이 바람직하다.

## 9. 도메인에 맞는 현실적인 판단

우리는 **개발 업무의 기억**을 우선 생각했다. 사용자가 실제로 원하는 것은 때때로 "예전에 논의한 정확한 결정과 이유"이고, 때때로 "지금 바뀐 코드가 무엇을 하는가"다. 후자는 메모리보다 **현재 코드**를 확인하는 편이 맞다. Git 설계 문서·테스트는 공식 산출물의 정합성 증거이고, 기억은 그 산출물에 이르게 된 과거 맥락을 찾는 역할일 수 있다.

복잡한 알고리즘을 도입하기 전에 **사람이 명시적으로 저장한 소수의 결정**과 기본 검색만으로도 실용성이 충분한지 관찰할 가치가 있다. 복잡한 알고리즘은 그 한계를 확인한 후 선택할 수 있다. 반대로 자동 수집이 중요한 환경이라면 MCP만으로 도구가 불리지 않는 문제가 기억 알고리즘보다 먼저 해결돼야 할 수 있다.

## 10. 이 문서를 계속 사용하는 방법

- 연구 결과는 **문제 / 관측 / 가설 / 대안 / 시험 조건 / 결과 / 다음 판단**으로 기록하는 것이 좋다.
- 어떤 수치를 고정하거나 기술을 채택하려면 그 근거가 되는 **실제 데이터와 실패 사례**를 함께 적는다.
- 사내에서 생긴 원문, 스택 트레이스, 고객/회사 정보, 코드 또는 업무 결정을 외부 저장소로 옮기지 않는다.
- 기존 Architecture/Phase 0 계약과 충돌하는 변경이 생기면 영향을 받은 원본·권한·삭제·엔진 교체 불변조건을 검토한다.
- 이 문서는 앞으로 달라져도 된다. 지금의 미결정 목록이 미래의 팀에 대한 명령으로 작동하지 않도록 한다.
