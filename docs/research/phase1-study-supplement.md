# Phase 1 스터디 보충 메모 — 논문·코드·기존 설계 사이의 판단 근거

> **작성 맥락:** 2026-11-17, 외부에서 논의한 내용과 공개 Hindsight 논문/코드 및 MemoryLACE 논문을 다시 대조하여, 사내 로컬 Phase 1 개발에 전달할 *추가 배경*을 정리했다.
>
> **문서 성격:** [기존 연구 노트](hindsight-memorylace-insights.md)와 [열린 연구 질문](future-experiments-and-questions.md)의 **보충 설명**이다. Phase 1 구현 계획, 확정 ADR, 특정 논문 복제 명세 또는 내부 개발 현황 보고서가 아니다. **[기존 방향]**, **[공개 연구의 관찰]**, **[추가 해석/설계 가설]**, **[미결정]**을 구분한다. 기존 문서와 내용이 겹치면 해당 문서를 기본 설명으로 읽고, 이 문서는 *왜 그 질문이 중요한가*에 초점을 맞춘다.
>
> **데이터 경계:** 외부 GitHub의 기존 코드와 공개 연구 자료만 참고했다. 사내망에서 생성된 코드·기록·시험 결과·구성·데이터를 보거나 반출하지 않았다. 이후 실제 변경과 결정은 사내 승인된 저장소가 기준이다. 외부 GitHub의 \`main\`이 사내 코드의 최신 상태를 나타낸다고 가정하지 않는다.

## 1. 이 프로젝트에서 지키려던 생각: 메모리를 단순한 문서 검색과 동일시하지 않는다

**[기존 방향]** 장기적인 목표는 한 사용자의 경험이 에이전트/세션/PC를 넘어 계속 활용되는 것이다. 하지만 "무엇을 저장했다"와 "다음에 무엇을 기억해야 한다"는 같은 질문이 아니다.

- **기록(Experience)**: 누가 무엇을 말했다/했다/제출했다고 기록돼 있는가.
- **기억 산출물(Memory Artifact)**: 엔진이 무엇을 추출·요약·연결했는가.
- **회상 결과(Retrieved evidence)**: 해당 질의에서 어떤 근거를 찾아 보여주었는가.
- **최종 판단(Agent answer/decision)**: 에이전트가 그 근거와 현재 코드·지침을 비교해 무엇을 답했는가.

**[추가 해석]** 이 네 층이 붙어버리면 Phase 1의 품질 실패를 검증하기 어렵다. 좋은 요약이 틀린 검색을 구하지 못하고, 올바른 검색 결과가 에이전트의 부적절한 확신을 막아주지도 않는다. 그래서 "메모리 엔진 성능"이라는 하나의 점수보다 **수집→형성→조회→사용**의 단계별 책임과 검증 가능성이 더 중요하다고 보았다.

특히 메모리 저장 내용은 *정보*이지 *명령*이 아니다. 과거 대화에서 등장한 지시나 프롬프트를 높은 우선순위의 현재 작업 명령으로 승격해서는 안 된다.

## 2. Namespace 제거가 Phase 1에 주는 의미

**[이미 채택한 Phase 0 방향]** 서버 인스턴스 하나가 **단일 기억 공간 하나**를 관리하고, 여러 Principal/기기가 그 기억을 공유한다. Namespace·Grant를 제거했다. 이는 *여러 프로젝트를 분리하지 않고 장기적으로 교차 프로젝트 연상을 시도할 자유*를 얻기 위한 결정이기도 하다.

이 말은 아래 두 결론과 **동일하지 않다**.

1. "모든 기억을 매 질의마다 전체 검색해야 한다" — **아니다.** 엔진은 프로젝트, 사건, 시점, 엔터티, 대화 문맥을 관련성 단서로 이용하거나 검색 범위를 조정할 수 있다.
2. "서로 다른 보안 수준의 데이터도 LLM이 분류하면 안전하게 섞을 수 있다" — **아니다.** 단일 인스턴스는 단일 신뢰·접근 경계라는 운영 전제가 있다. 다른 신뢰 경계는 엔진의 토픽 분류가 아니라 서버/배포/보안 정책에서 분리해야 한다.

**[추가 해석]** \`project\`, \`repo\`, \`session\`, \`harness\`, \`speaker\`, \`occurred_at\` 같은 메타데이터는 사전 분리용 네임스페이스가 아니라, **검색/시간/귀속 판단을 돕는 약한 문맥 신호**일 수 있다. 이런 신호의 부재를 임의로 만들어 채워 넣거나, 문자열 일치만으로 정보 접근 권한을 변경해서는 안 된다. 출처 locator가 실제 사실 검증을 의미하는 것도 아니다.

## 3. Hindsight와 MemoryLACE는 같은 질문에 대한 두 가지 다른 관찰 렌즈

| 관점 | Hindsight 논문의 강조 | MemoryLACE 논문의 강조 | 우리가 얻은 설계 질문 |
| --- | --- | --- | --- |
| 기억의 표현 | 맥락을 담는 narrative fact, 사실/경험/관찰/의견의 인식론적 분리 | 출처 있는 atomic 자연어 기억과 lifecycle 링크 | 의미가 뭉개지지 않는 최소 단위는 무엇인가 |
| 변하는 정보 | 관찰 요약·의견의 갱신과 근거 기반 reflection | 반복, supersession, contradiction의 국소적 연결 | "업데이트"가 옛 증거의 삭제를 뜻하는가 |
| 검색 | lexical/semantic/entity/temporal 경로의 결합 | 활성 단서에서 역사/상충 증거로 확장 | 관련성 상위 결과와 *판단에 필요한 증거 묶음*은 다른가 |
| 비용 | 풍부한 구조화·추론·갱신에 드는 비용을 감수 | 전역 반영보다 국소 lifecycle 관계에 집중 | 실제 질문에서 어느 추가 비용이 유익한가 |
| 결과의 의미 | 사실/관찰/의견/신뢰의 구분 | 현재/과거/지지/모순의 구분 | 이용자에게 과거 상태·불확실성을 어떻게 보여줄까 |

**[미결정]** Narrative 대 Atomic, 그래프 대 sparse lifecycle, retain/recall/reflect의 구현 경계, 모델·점수식·시간 함수는 **선택하지 않았다**. 두 연구의 강점 일부를 조합할 수도 있고, 내부 데이터에서는 단순한 방식이 더 나을 수도 있다.

**중요한 명칭 주의:** 논문의 "agent experience network"와 우리 서비스의 **원본 Experience**는 서로 다른 개념이다. 논문 용어를 그대로 공통 DB 스키마로 고정하지 말자.

## 4. 기억을 형성할 때 발생하는 '조용한 손실' 문제

**[공개 구현의 관찰]** Hindsight의 현행 Retain 개발 문서는 추출 정책(\`retain_mission\`)이 어떤 문서의 모든 내용을 제외하면 입력 처리는 완료돼도 **생성된 memory unit이 0개**일 수 있으며, 추출이 완전히 결정적이지 않아 재처리가 필요할 수 있다고 설명한다. 이 문서의 상세 동작은 원 논문과 구별해야 한다. [Hindsight Retain docs](https://github.com/vectorize-io/hindsight/blob/main/hindsight-docs/docs/developer/retain.md)

**[추가 해석]** 이것은 우리 Phase 0의 "접수 성공은 검색 가능 보장이 아님"이라는 규칙보다 한 단계 더 구체적인 문제를 보여준다.

- **기술적으로 처리 완료**: Job이 실패하지 않았다.
- **가공 산출물 존재**: 파생 Memory가 1개 이상 생성됐다.
- **정보 보존 충분성**: 앞으로의 질문에 필요한 이유·예외·시점·숫자·식별자가 남았다.
- **실제 회상 가능**: 질의 방식이 바뀌어도 필요한 근거를 다시 찾을 수 있다.

서버가 모든 Job을 성공 처리해도, 추출 전략이 너무 공격적이면 실제로 가장 필요한 기억이 사라질 수 있다. Narrative는 너무 넓으면 특정 사실을 찾기 어렵고, Atomic은 너무 짧으면 "왜/언제/누가/어떤 조건에서"를 잃는다.

**[미결정/검증 질문]** 추출 결과가 0개인 경우를 언제 정상으로 받아들일까? 정보 손실을 어떤 샘플링/질의로 감지할까? 원본 재처리가 가능하다는 사실만으로 손실이 허용되는가? 어느 길이의 원문 창을 근거로 유지해야 하는가?

## 5. 출처와 신뢰: '근거가 있다'는 사실도 여러 층위다

**[기존 방향]** Phase 0의 \`source_ref\`는 검증되지 않은 위치 주장이고, \`actor_reported\`는 클라이언트가 보고한 화자 정보다. \`submission.evidence_refs\`는 아직 지원하지 않는다. 원본 Experience를 저장했다는 사실만으로 텍스트의 내용이 참이라는 보장은 없다.

Phase 1에서 구조화된 기억을 다루면 아래 구분이 더 중요해질 수 있다.

| 구분할 것 | 예시 | 함정 |
| --- | --- | --- |
| **출처 기록** | "이 내용은 Experience 17에서 추출" | Experience 자체가 사실을 증명하지 않음 |
| **인용/지지 근거** | "원문 이 부분이 그 요약을 뒷받침" | 요약의 일부만 뒷받침하거나 조건을 누락할 수 있음 |
| **중복/반복** | "세 번 같은 말을 들었다" | 모두 같은 최초 소스의 복사라면 독립 증거 3개가 아님 |
| **모순** | "A는 X, B는 Y라고 보고" | 반드시 어느 쪽이 틀린 것은 아님; 시점·범위·주체가 다를 수 있음 |
| **신뢰/확신** | "엔진이 0.9로 판단" | 모델의 확신과 정보의 검증 수준은 다름 |

**[추가 해석]** Hindsight의 observation이나 MemoryLACE의 merge/supersession은 원본 여러 개를 엮을 수 있다. 따라서 **여러 원본을 참조하는 파생 기억의 근거 사슬**과 **그중 일부를 삭제/정정했을 때 남은 파생 기억이 여전히 유효한지**는 초기부터 관심을 가질 만한 설계 압력이다.

하지만 "모든 파생 기억은 원본 하나만 참조" 또는 "원본 하나 삭제 시 연결된 모든 요약을 무조건 영원히 삭제" 같은 규칙도 지금 미리 확정하지 않는다. 어떤 다중 근거 모델을 도입하느냐에 따라 **관계 제거·재계산·무효화 범위**가 달라진다. 그럼에도 삭제된 원본의 내용이 기존 요약·캐시·관계·이전 Generation을 통해 재노출되어서는 안 된다는 서비스 정책은 유지된다.

## 6. 시간은 한 개의 timestamp가 아니다

**[공개 연구의 관찰]** Hindsight 논문은 사건의 발생 범위와 mention time을 구별한다. MemoryLACE는 시간에 따른 업데이트·대체/모순의 구분을 핵심으로 삼는다.

**[추가 해석]** 개발 기억에서는 최소한 다음 질문이 분리된다.

- **언제 발생했나?** ("금요일에 장애가 발생했다.")
- **언제 알게/언급/기록됐나?** (월요일 회고에서 지난 금요일을 보고했다.)
- **언제부터 언제까지 유효한 선택이었나?** (기술 결정이 이 주간에만 적용됐다.)
- **언제 시스템이 처리했나?** (월요일 밤에 Worker가 인덱싱했다.)

이것들은 동일한 날짜로 축약되면 안 된다. 특히 "현재 구현은 무엇인가", "그때는 무엇으로 결정했는가", "지난주에 왜 변경했는가"는 서로 다른 질의다.

**[미결정]** Phase 1에서 모든 시간 축을 별도 DB 필드로 만들자는 뜻이 아니다. 원문이 제공하지 않는 날짜를 추론해 확정하지 않는 것, 상대시각을 해석할 때 기준 시점이 필요하다는 것, 시간 불확실성을 보존할 수 있는지가 더 근본적인 질문이다.

## 7. 누가 말했는가: 단일 기억 공간, 여러 에이전트의 시점

**[공개 구현의 관찰]** Hindsight의 Retain 문서는 세계에 관한 주장(\`world\`)과 은행의 에이전트가 실제로 경험한 일(\`experience\`)을 구분할 때 **어떤 화자의 1인칭인가**가 중요하다고 설명한다. 누군가 "I fixed the bug"라고 말해도 그 "I"가 사용자/제3자/에이전트 누구인지에 따라 의미가 바뀐다. [Hindsight Retain docs](https://github.com/vectorize-io/hindsight/blob/main/hindsight-docs/docs/developer/retain.md)

**[추가 해석]** 우리 시스템은 개인 하나가 소유하지만 여러 에이전트의 기억을 함께 저장한다. 따라서 **소유자는 한 명**이어도 **행위자·화자·관찰자·대상**은 여러 명일 수 있다.

- 에이전트가 "**제가 수정했어요**"라고 주장했다는 로그와 실제 Git 커밋이 존재한다는 사실은 다른 증거다.
- 사용자가 "**내가 결정했어**"라고 한 것과 에이전트가 "사용자 결정으로 보인다"고 요약한 것은 같지 않다.
- Hindsight의 bank-per-agent 패턴을 우리 서버의 필수 모델로 가져올 필요는 없다. 대신 다중 화자의 관점과 귀속 오류를 엔진 평가에 넣을 가치는 있다.

**[미결정]** 화자 확인/행위 검증을 얼마나 자동화할지, 외부 도구/코드 증거와 어떻게 연결할지, 엔진이 작성자를 얼마나 신뢰할지는 미정이다.

## 8. 통합·대체·모순은 검색과 삭제와는 또 다른 연산이다

**[기존 논의]** "이전에 DB A로 결정했고 나중에 DB B로 바꿨다"는 사례를 단일 최신 사실만 남기는 방식으로 처리하면 과거 의사결정과 변경 이유를 물을 수 없다.

**[MemoryLACE 관찰]** sparse merge/supersession/contradiction 관계가 있다는 사실은 유용하지만, 그 링크가 곧 근거에 대한 논리적 증명은 아니다. 두 사실이 같은 순간/범위에서 경쟁하는지, 단순히 **서로 다른 시점의 상태**인지 확인해야 한다.

**[추가 해석]** "새 정보를 넣는다"라는 하나의 입력이 서로 다른 결과를 낳을 수 있다.

1. **지지/반복**: 독립된 추가 증거일 수도, 동일 소스를 복사한 중복일 수도 있다.
2. **변경/대체**: 옛 결정은 역사적으로 유효하지만 현재 작업에는 적용되지 않을 수 있다.
3. **모순/불확실성**: 당장 해결할 근거가 없으면 상충 상태를 보존하는 편이 더 정직할 수 있다.
4. **정정**: 과거 제출 오류를 정정한 것이며, 실제 세계의 상태 변경과는 다를 수 있다.
5. **삭제/접근 철회**: **서비스 정책**에 따라 더 이상 보이면 안 되는 데이터/접근을 다루며, supersession과 동의어가 아니다.

이 구분을 먼저 사고하면, 나중에 어떤 Graph/Atomic/Narrative 모델을 택하든 "현재 답"과 "과거 상태"를 별도로 검증할 수 있다.

## 9. Hindsight 논문과 GitHub 구현을 같은 시점의 동일 명세로 읽지 않는다

**[공개 자료의 관찰]** Hindsight 원 논문은 네 논리적 네트워크와 Retain/Recall/Reflect, TEMPR/CARA 구조를 제시한다. 반면 **2026-11-17에 확인한 GitHub main README**에는 논문 외에 운영 통합, **mental models/pages**, **decision models**, 코딩 에이전트용 자동 연동 등 확장된 기능 설명이 등장한다.

따라서 소스 코드와 논문을 비교할 때 세 가지를 구분하는 게 좋다.

- **논문이 주장·평가한 구조/성능**: 원문과 그 실험 조건에서 확인한다.
- **GitHub 특정 버전의 실제 동작**: 해당 commit/tag, 기본값, 프롬프트, 의존성, 데이터 모델을 확인한다.
- **우리 시스템에 적용해 확인한 결과**: 동일한 원본·질의·예산·권한·환경에서 별도로 측정한다.

**[추가 해석]** 최신 Hindsight의 기능 수가 많다는 이유로 그 모두를 Phase 1의 필수 기능으로 삼지 않는다. \`reflect\`는 단순 \`recall\`과 달리 LLM 추론을 수반하고 경우에 따라 상태를 갱신할 수 있다. "검색만 하려던 요청이 기억/의견을 쓰는 작업이 되지 않는가"를 분리해 검토할 이유가 있다.

또한 Hindsight의 **bank**는 여러 독립 사용자/에이전트를 격리할 때 쓰는 제품 개념이다. 우리 서비스가 Namespace를 제거한 결정을 되돌려야 한다는 근거가 아니다. 다른 신뢰 경계는 서버 배포에서 다루고, 의미적 분류는 엔진이 정할 수 있다.

## 10. 엔진을 교체할 때 숨어 있을 수 있는 상태

**[기존 방향]** Phase 0는 원본 Experience와 독립된 Generation을 만들고 비교/전환/조건부 롤백할 수 있게 했다. \`reference/1\`·\`reference/2\`는 유효한 기준선이다.

**[추가 해석]** 하지만 LLM 추출·중복 통합·요약·의견 갱신·시간 감쇠가 들어오면 "같은 원본을 다시 처리"의 의미가 복잡해진다.

- 최신 원본 집합으로 **그때 새롭게 계산한 결과**와, 과거에 실제로 진화한 **엔진 상태의 정확한 재현**은 다를 수 있다.
- 기존 관찰/의견/연결 관계를 쓰는 점진 갱신 엔진은 \`source_batch → independent drafts\`만으로 자신의 의미를 다 표현하지 못할 수 있다.
- 비결정적 모델은 동일 프롬프트를 반복해도 byte-identical 기억을 보장하지 않는다. 어떤 모델/프롬프트/정규화/인덱스/시점/상태가 결과를 만들었는지 기록하는 편이 더 현실적일 수 있다.
- 후보 Generation을 만드는 도중 삭제·철회가 발생하면, 별도 캐시/검색 색인/관계까지 **현재 정책으로 최종 확인**돼야 한다.

**[미결정]** 이벤트 로그, 체크포인트, 엔진별 상태 저장소, 전체/부분 재계산의 채택을 지금 결정하지 않는다. **두 번째 실제로 다른 엔진이 나타난 뒤** 현재 Engine Boundary가 무엇을 놓치는지 평가하는 것이 원래 의도였다.

## 11. 기억의 '약화/잊힘'과 회상 편향

**[기존 논의]** 기억을 **남겨둘 가치**와 질의에서 **쉽게 떠오를 가능성**을 독립적으로 생각해 보고 싶었다. 시간이 지나 낮은 우선순위가 된 기억도 깊은 검색/새 문맥으로 되살리는 방법은 관심 있는 연구 주제이지만, 구체 점수식·감쇠 함수·사람의 망각 모델을 채택하지 않았다.

**[추가 해석]** 사용 횟수나 검색 노출 빈도로 접근성을 높이면 **자주 보이는 기억만 더 자주 사용되는 자기강화 편향**이 생길 수 있다. 반대로 중요하지만 평소에 덜 호출되는 기억을 완전히 잃을 위험도 있다. 그러므로 "현재 top-k에서 잘 안 보임"은 "보존 가치 없음"과 다른 평가 항목이다.

또한 deletion/revocation은 연구용 forgetting과 완전히 다르다. 삭제 정책 위반인 데이터를 "deep recall"로 되살리는 일은 허용되지 않는다. 어떤 강도 점수를 도입해도 정책상 유효한 데이터만 후보가 될 수 있다.

## 12. Phase 1 평가를 설계할 때 더 선명하게 구분하면 좋은 것

기존 [연구 질문 문서](future-experiments-and-questions.md)의 평가 범주에 아래 *해석상 구분*을 덧붙인다.

| 관측 | 무엇이 유용한가 | 잘못된 결론 |
| --- | --- | --- |
| 입력→추출 개수 | 입력별 0개/과다 추출, 정정 필요율 | "처리 성공=좋은 기억 생성" |
| 원문→파생 근거 | 이유·조건·수치·화자·출처 보존 | "출처 ID만 있으면 요약이 참" |
| 현재/과거 질문 | 변경 전후 둘 다 적절히 답하는가 | "최근 기억을 반환하면 최신 사실" |
| 반복/모순 사례 | 독립 증거·동일 출처 복사·오류 정정 구분 | "3번 들었으니 3배 확실" |
| 검색 후보→반환 | top-N과 토큰 예산·재순위화로 누락되는 지점 | "검색 miss는 저장/추출 실패" |
| MCP 도구→Agent 답변 | 도구 미호출, 호출 후 miss, 반환 후 미사용 | "엔진 품질이 낮아 자동 호출 안 함" |
| 비용/재처리 | 추출/통합/검색별 지연·연산·비결정성 | "전체 QA 점수가 높으니 운영이 우수" |
| 삭제·철회·복원 | 다중 근거와 관계/캐시에 남은 재노출 | "논리적 대체=안전한 삭제" |

**[추가 해석]** 가능하면 좋은 기억을 저장했어도 **일부러 대답하지 않는 것(abstention)**이 올바른 질문을 포함하는 게 중요하다. 원본이 없거나, 시점이 모호하거나, 동일한 근거가 모순을 해결하지 못했다면 "확인할 수 없음"은 정상적인 결과일 수 있다.

**[미결정]** 특정 벤치마크, 목표 정확도, LLM judge, 점수 가중치 또는 정답 데이터셋의 형태를 강제하지 않는다. 공개 논문끼리 다른 환경에서 얻은 절대 점수를 직접 비교해 우열을 확정하지 않는다.

## 13. 이후 개발자가 선택할 수 있는 '연구 카드' 틀 (지시사항 아님)

각 기술 후보를 구현하기 전에 다음만 짧게 기록해도 왜 도입했는지 나중에 복원하기 쉽다.

> **관찰된 실패:** 예) 과거 DB 결정과 현재 결정을 혼동함  
> **원인 가설:** 시간 구분 또는 대체 관계가 검색에 반영되지 않음  
> **비교할 접근:** 현재 Reference / 시간 재정렬 / Lifecycle Evidence Unit  
> **같이 유지할 조건:** 같은 원본·질의·모델/토큰 예산·접근 정책  
> **예상 이득과 비용:** 현재/과거 정확도 개선 vs 추가 LLM 호출·재처리·상태 복잡도  
> **위험:** 과거 증거 소실, 출처 미표시, 삭제 후 캐시 잔존  
> **미결정으로 남길 항목:** Graph 스키마, Confidence 함수, 특정 모델 등

특히 단일 기억 공간의 장점인 **교차 프로젝트 경험의 재사용**을 검사하되, 프로젝트 이름이 유사하다는 이유로 서로 다른 문맥/시점을 혼동하는 오탐도 관찰할 수 있다.

## 14. 이 보충 문서가 하지 않는 것

- Hindsight를 복제하거나 MemoryLACE를 기반 엔진으로 **확정하지 않는다**.
- Atomic/Narrative, 단일/다중 인덱스, Graph/관계형, temporal schema, confidence/forgetting 함수, 외부/로컬 LLM을 **결정하지 않는다**.
- 우리 Phase 0 시스템의 DB·MCP 공통 API에 새 의미 분류나 그래프 타입을 **요구하지 않는다**.
- 사내에서 진행 중인 Phase 1 구현 상황을 안다고 주장하지 않는다.
- 새 연구 결과·외부 공개 벤치마크를 **사내의 실제 성능 근거로 제시하지 않는다**.
- 더 많은 기능을 만드는 것을 성공 조건으로 삼지 않는다.

이 프로젝트의 출발점은 특정 논문 복제품이 아니라, **경험의 출처·권한·생명주기를 지키면서 장기 기억의 유용성을 실험적으로 개선할 수 있는 개인 소유 시스템**이라는 점을 유지한다.
